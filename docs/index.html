Chapter 01

What is Java, and why should you care?

Java is a class-based, statically-typed language that compiles to bytecode and runs on a virtual machine. That last part is the whole trick: write your program once, and it runs identically on Windows, macOS, Linux, a phone, a fridge or a mainframe — with a garbage collector handling memory so you never free a pointer.

Let's start at the very beginning. Every program you run is ultimately a set of instructions for a CPU and a set of bytes in memory. Some languages sit far above that reality: Python and JavaScript hand your source to an interpreter that reads it line by line. C and C++ compile straight to machine code for one specific CPU and leave you personally responsible for never freeing memory twice, never writing past the end of an array, and never letting two threads touch the same variable at once. Get it wrong and your program leaks, crashes, or gets exploited.

Java found a third path. Your source compiles not to machine code, but to bytecode — a portable, CPU-independent instruction set. A program called the JVM (Java Virtual Machine) translates that bytecode into real machine code for whatever hardware it's actually running on, while a garbage collector reclaims memory automatically. You get C++-grade performance after warm-up, memory safety without a borrow checker, and "write once, run anywhere" that isn't a marketing slogan — it's the architecture.

The three pillars of Java

♻️

Automatic memory

A garbage collector finds and reclaims unreachable objects. No malloc, no free, no double-free, no dangling pointers — an entire class of memory bugs simply cannot happen.

📦

Everything is an object

Java is squarely object-oriented: you model your domain as classes with state and behaviour, and the type system enforces the contracts between them at compile time.

🌍

Write once, run anywhere

Bytecode is platform-neutral. The same JAR runs on a laptop, a Kubernetes cluster or an Android handset — the JVM adapts to the hardware, not your code.

💡 The one-sentence version

Java is "C++ without the pointer arithmetic, plus a virtual machine that makes your build artifact portable and a collector that makes your memory management boring." It's a language built around a single idea: reliability at scale, over decades, across teams.

A short history

1991

A side project called "Green"

James Gosling and colleagues at Sun Microsystems set out to build software for interactive television set-top boxes. The language — originally called Oak, after the tree outside Gosling's office — needed to run on cheap, unreliable consumer devices. The constraints of that problem shaped everything that followed.

1995

Java debuts with applets

Sun launches Java 1.0 alongside the Netscape browser. Applets — tiny programs running inside a web page — are a sensation for about five years. The real innovation nobody noticed yet: bytecode and the "write once, run anywhere" promise.

2004 · Java 5

The language grows up

Generics, enhanced for-loops, autoboxing, varargs, enums and the java.util.concurrent package arrive in one enormous release. This is the version that made Java viable for serious concurrent server work.

2006–2010

Sun falls, Oracle rises

Sun open-sources the JDK under GPLv2 — one of the most consequential licensing decisions in software history. In 2010 Oracle acquires Sun, and with it, Java. A long litigation interlude follows, then settles.

2014 · Java 8

Lambdas and streams change the style

The single most important release for day-to-day code. Lambdas, method references and the Stream API let Java finally express what you want instead of how to loop for it. Most Java codebases still look like "Java 8 style" today.

2017 →

OpenJDK, six-month cadence, JetBrains

Java moves to OpenJDK with a predictable six-month release train — records in 16, sealed types in 17, virtual threads in 21. Meanwhile JetBrains ships Kotlin in 2016 (open-sourced 2017) and Google makes it Android's preferred language in 2019.

Today

The most-used runtime on Earth

An estimated 3 billion devices run Java. It underpins banking, insurance, government systems, big data (Hadoop, Kafka, Spark), Android, and the back end of a huge share of the web. Kotlin, Scala, Groovy and Clojure all run on the same JVM.

Where Java sits in the language landscape

It helps to know what Java is not. It isn't the fastest — C and C++ beat it on raw throughput and it can't match Rust's compile-time memory guarantees. It isn't the most concise — Kotlin, Python and JavaScript all say more with less. It isn't the most cutting-edge. What Java is, is the most dependable combination of "fast enough", "safe enough", "portable everywhere" and "nobody gets fired for choosing it" that has ever existed.

What makes the JVM's guarantees possible

The magic isn't one trick, it's a stack of them. Understanding this stack is the difference between "I can write Java" and "I understand what the JVM is doing while my code runs":

1 · .java / .kt Your source. javac compiles Java; kotlinc compiles Kotlin. Both produce bytecode — the same format, in the same .class files.
→
2 · .class files Platform-neutral instructions packed into a JAR. This is why a Linux build runs on Windows — the artifact contains no machine code for any particular CPU.
→
3 · Class loader Loads classes into the JVM on demand, in a strict hierarchy (bootstrap → platform → application), verifying bytecode as it enters so corrupt code can't run.
→
4 · JIT compiler The hot parts of your program — the 5% doing 95% of the work — get compiled to native machine code and cached. Everything else is interpreted.
→
5 · GC + threads The garbage collector reclaims memory you can't reach, and the OS schedules your platform threads. You write logic; the runtime does the bookkeeping.
🧠 Why the JIT matters more than you'd think

A compiler that only sees your source has to guess which paths are hot. A JIT compiler watches your program run and optimises the code that actually executes — inlining small methods, unboxing types it has proven are always integers, even speculatively removing null checks after it has verified a value is never null. In long-running server processes, Java routinely catches up to and sometimes beats C++ on steady-state throughput, because it's optimising with real evidence.

Hello.java
public class Hello {
    public static void main(String[] args) {
        String name = args.length > 0 ? args[0] : "world";
        System.out.printf("Hello, %s!%n", name);
    }
}

Compile it, run it, and watch the two-step process that defines the entire platform:

terminal
javac Hello.java          # step 1: source -> Hello.class (BYTECODE, not machine code)
java Hello Ashton         # step 2: JVM loads the bytecode and runs it
# Hello, Ashton!

javap -c Hello | head -12 # look at the actual bytecode instructions

That .class file is the whole point. It contains no x86, no ARM, no machine code for any particular CPU — just JVM instructions like aload_0, invokevirtual and areturn. Any device with a JVM can run it, which is the reason a JAR built on Linux in 2010 still executes today on hardware that didn't exist then.

⚠️ Java's two honest weaknesses

1. Startup and memory footprint. Booting a JVM costs time and tens of megabytes before your code runs — irrelevant for a server that lives for months, painful for a CLI tool or a serverless function. Project CRaC and Project Loom's virtual threads both attack this from different angles.

2. Verbose boilerplate. A class that holds four fields used to need fifty lines of getters and setters. Records, var, lambdas and text blocks have shrunk this dramatically — and Kotlin shrinks it to almost nothing, which is exactly why Part II exists.

🚫 Myth: "Java is slow"

This belief is roughly twenty years out of date. Modern Java — thanks to the JIT, escape analysis, biased locking and compact strings — sits in the same performance tier as C# and within striking distance of C++ for most business logic. Where Java genuinely does lose is startup time and small-memory footprints, which is a different claim entirely, and one the ecosystem is actively fixing.

Chapter 02

Installing Java & your first program

Install one JDK, run a real program in a single command, and learn the four tools you'll type every day — java, javac, javap and jshell — plus the project layout and editor setup that keep everything working long after this chapter.

Newcomers lose their first hour to the toolchain, never the language: java: command not found, a JDK installed in three places, an IDE still pointing at Java 8 because that shipped with the laptop, or a build tool quietly downloading its own compiler and writing class files your editor can't see. None of that is Java's fault, and all of it disappears with one clean install and five commands you can type from memory.

Install the JDK, not a runtime. The old "JRE vs JDK" confusion dates from Java 8, when Oracle shipped two installers and only one of them could compile. A modern JDK — around 180 MB — contains the compiler, the runtime, the disassembler and the REPL, and it's what every IDE, build tool and tutorial expects to find. By the end of this chapter you'll have that JDK on PATH, a program running on it, and a skeleton you'll fill for the next thirty chapters.

Install a JDK in 60 seconds

Pick whichever block matches your machine. SDKMAN is the one I'd choose if you have no other constraints: it installs side-by-side JDKs and switches between them with one command, which matters the first time a project demands Java 17 while your default is 21.

terminal
# SDKMAN — version manager for Java, Kotlin, Gradle (macOS / Linux)
curl -s "https://get.sdkman.io" | bash
sdk list java | grep -m6 tem        # Temurin builds, pick a 21.x id
sdk install java 21.0.5-tem
sdk default java 21.0.5-tem

# Debian / Ubuntu — Ubuntu 24.04+ and Debian 13 ship OpenJDK 21
sudo apt update && sudo apt install -y openjdk-21-jdk-headless

# macOS
brew install --cask temurin@21

# Any platform: Temurin tarball straight from Adoptium's API
BASE="https://api.adoptium.net/v3/binary/latest/21/ga/linux/x64/jdk"
curl -L -o jdk21.tar.gz "$BASE/hotspot/normal/eclipse?project=jdk"
tar -xzf jdk21.tar.gz && export PATH="$PWD"/jdk-21*/bin:$PATH

# Verify — all three must agree on 21
java -version                       # runtime (prints to stderr)
javac -version                      # compiler
echo "$JAVA_HOME"                   # IDEs & build tools read this one
🧠 Two java on one machine

java -version and javac -version coming from different installs is the single most common "it compiles here and fails there" bug — the compiler targets 21, the launcher runs an older runtime, and you get an unsupported class file version error. Make them identical, set JAVA_HOME to the JDK root (the directory containing bin/), and let your IDE read that rather than shipping its own bundled runtime.

Kotlin rides on the same JVM, so this JDK comes first there too: brew install kotlin or sdk install kotlin after the JDK, then kotlinc -version to confirm both halves work.

Your first program, two ways

Type this into a file named Hello.java. The filename must match the public class — that's not a convention, it's a rule the compiler enforces.

Hello.java
public class Hello {
    public static void main(String[] args) {
        String who = args.length > 0 ? args[0] : "world";
        System.out.println("Hello, " + who + "!");
        System.out.println("Running Java " + Runtime.version().feature());
    }
}

Now run it — first the modern shortcut, then the two-step you'll use inside every real project:

terminal
java Hello.java                   # Java 11+: compiles in memory, runs, discards
# Hello, world!
# Running Java 21

javac Hello.java && java Hello    # the classic two-step: compile, then run
java Hello Ada                    # args work identically both ways
# Hello, Ada!

javap -c Hello                    # dissect the class file you just produced
#   public static void main(java.lang.String[]);
#     Code:
#        0: aload_0
#        1: arraylength
#        2: ifle        11         # args.length > 0 ? args[0] : "world"
#        5: aload_0
#        6: iconst_0

#        8: goto        13

Those mnemonics — aload_0, arraylength, ldc, invokevirtual — are the entire execution model of the platform. There is no x86 and no ARM in that file, which is precisely why the artifact is portable:

1 · Hello.java UTF-8 source, one public class per file, package implied by folder.
→
2 · javac Parses, type-checks, resolves symbols — and emits Hello.class: portable JVM bytecode, still no machine code.
→
3 · class loader java boots a JVM, loads your class and verifies the bytecode before a single instruction executes.
→
4 · interpreter → JIT Interpreted first, then the hot path is compiled to native code and cached. main returns, the JVM shuts down.
💡 When the single-file launcher is the right tool

java Script.java compiles into memory, runs, and leaves no .class files behind — perfect for a 30-line algorithm experiment, an interview question, or a script you'll delete in ten minutes. It stops being right the moment you have two files, a dependency, or a test: that's a project, and Chapter 17 gives you a build tool for it. (Java 22 widened the launcher to whole multi-file programs under JEP 458; on Java 21 it's strictly one source file.)

jshell — Java with training wheels off

jshell is the read-eval-print loop that shipped with Java 9. It's where you settle arguments about operator precedence, check what Math.round(-2.5) actually returns, or prototype a loop before committing it to a class. Snippets compile and run on Enter; expressions show you their value.

The java flags you'll actually meet

Nobody needs the full 300-option reference. These four come up in your first month, and they're worth understanding rather than copying:

terminal
java -Xmx512m -jar app.jar        # cap the heap at 512 MB
java -Xms1g -Xmx4g -cp target/classes com.example.App
java -ea -Dfile.encoding=UTF-8 App # assertions on, one system property
java --enable-preview App          # opt in to preview features
javac --enable-preview --release 21 App.java   # ...and match it at compile

-Xmx sets the maximum heap — the difference between an OutOfMemoryError you caused and a garbage collector that keeps up. -jar runs the class named in the manifest of a JAR, which is how every shipped Java application starts. -cp (a.k.a. --class-path) is where the JVM searches for your classes and libraries. And --enable-preview opts into features that might still change before they're finalized: it must be passed to both javac and java, the class file is marked as preview-only, and it has no business in production.

Make it interactive

A program that only prints is a demo. Two inputs exist in Java: the argument array your launcher hands over, and standard input, which is how you read from a pipe or a keyboard. Wire both into one file:

Greeter.java
import java.util.Scanner;

public class Greeter {
    public static void main(String[] args) {
        String name = args.length > 0 ? args[0] : prompt();
        System.out.printf("Hello, %s!%n", name);
    }

    static String prompt() {
        System.out.print("Who are you? ");
        return new Scanner(System.in).nextLine().trim();
    }
}

Run it three ways — java Greeter.java Ada for an argument, echo "Ada Lovelace" | java Greeter.java for a pipe, or bare java Greeter.java to be asked. The same program in Kotlin is three lines, and it runs on the JDK you already installed: kotlinc Greeter.kt -include-runtime -d greeter.jar, then java -jar greeter.jar Ada — or as a script, kotlin greeter.main.kts.

Chapter 03

Variables, types & strings

Java has eight primitive types and an ocean of objects. Knowing which is which — and how strings actually work — removes most early confusion.

Every variable in Java has a type fixed at compile time. Primitives hold raw values on the stack; objects are references to things on the heap. This split is the single most important fact about Java's memory model.

🔢

8 primitives

byte short int long float double boolean char. Never null, never boxed unless used as a generic type argument.

🧬

References

Any class type. A variable holds an address; two can point at the same object. null means "points at nothing".

📏

Everything is typed

Types are checked before a line runs. There are no implicit conversions except numeric widening.

Primitives.java
public class Primitives {
    public static void main(String[] args) {
        byte    b = -128;          // 8-bit  ·  -128..127
        short   s = 32_000;        // 16-bit
        int     i = 2_000_000_000; // 32-bit · the default for whole numbers
        long    l = 9_000_000_000L; // 64-bit · note the L suffix
        float   f = 3.14f;         // 32-bit · note the f suffix
        double  d = 3.14159;       // 64-bit · the default for decimals
        boolean ok = true;         // true or false — never 0/1
        char    c = 'A';           // 16-bit Unicode code unit, in single quotes

        System.out.printf("%d %d %d%n", b, s, i);
    }
}

⚠️ Floating point is not arithmetic

🚫 Myth: "Java passes objects by reference"

Java passes everything by value. For objects, the value is the reference. So you can mutate the object a method points at, but you can never rebind the caller's variable — reassigning a parameter inside a method affects only the local copy. The confusion comes from the word "reference" doing two different jobs.

Strings are special

String looks primitive but is a full object. Two things about it explain 90% of interview questions:

🧊

Immutable

Every "modification" returns a new String. Safe to share, cache and use as a map key. Also means a loop of concatenation creates many throwaway objects.

📚

Interned literal pool

Literals like "hi" live in one pooled instance. == can work by accident — but you should never rely on it.

Strings.java
String a = "hello";
String b = "hello";
String c = new String("hello");

System.out.println(a == b);   // true  — same pooled literal
System.out.println(a == c);   // false — c is a fresh object
System.out.println(a.equals(c)); // true

// Immutability: each call returns a NEW string
String upper = a.toUpperCase();
System.out.println(a);        // "hello" unchanged
System.out.println(upper);    // "HELLO"

// Concatenation in a loop: O(n²) churn
String acc = "";
for (int i = 0; i < 10_000; i++) acc += i;   // avoid

StringBuilder sb = new StringBuilder();        // do this
for (int i = 0; i < 10_000; i++) sb.append(i);
String done = sb.toString();
✅ String, StringBuilder, StringBuffer
  • String — immutable, for values that don't change.
  • StringBuilder — mutable, not thread-safe, fast. The default for building text.
  • StringBuffer — mutable and synchronized. Rarely the right choice today.
  • The compiler already turns + in one expression into a StringBuilder — the problem is only loops.

Control flow, arrays & records

Java's control flow is deliberately boring — if, switch, for, while — but pattern matching and switch expressions make it noticeably less verbose than it was a decade ago.

There is nothing exotic here: no unless, no implicit truthiness, no ternary-as-statement. What's changed recently is that switch can now match on types and return values, and if can bind a variable from a type test.

Flow.java
int score = 87;

// if / else if — no implicit truthiness, the condition MUST be boolean

else if (score >= 80) System.out.println("B");
else                  System.out.println("C");

// Enhanced for — the default for anything iterable
for (int n : new int[]{1, 2, 3}) System.out.println(n);

// Classic for — when you need the index

// Ternary — expression only, never a statement

⚠️ No fall-through surprises in modern switch

The classic switch required break on every case — forget one and execution silently continues. Since Java 14, switch expressions use -> syntax and never fall through. The old colon form still exists and still bites.

Switch, then and now

❌ Classic statement switch 
String desc;
switch (day) {
    case MONDAY:
    case FRIDAY:
        desc = "start slow";
        break;                       // forget this → fall through
    case SUNDAY:
        desc = "rest";
        break;
    default:
        desc = "grind";
}

Each case needs an explicit break, and desc must be declared outside for the compiler to prove it's assigned.

✅ Switch expression with pattern matching 
String desc = switch (day) {
    case MONDAY, FRIDAY -> "start slow";
    case SUNDAY          -> "rest";
    case SATURDAY        -> "projects";
    default              -> "grind";
};

// Java 21+: pattern matching — match on type
static String describe(Object o) {
    return switch (o) {
        case Integer n when n < 0  -> "negative int";
        case Integer n             -> "int: " + n;
        case String s              -> "string: " + s;
        case null                  -> "nothing";
        default                    -> o.getClass().getSimpleName();
    };
}

Exhaustive by construction, no fall-through, and when guards let you add conditions on the same pattern.

🧠 Exhaustiveness is a compile error

Chapter 05

Classes, objects & constructors

A class is a description and an object is an allocation — internalise that one split and Java's constructors, access modifiers, static, equals() and records stop being a list of rules to memorise and become the obvious consequences of how instances are born, shared, compared and discarded.

You can write a surprising amount of Java with arrays and local variables. Then you inherit a module where account numbers live in one array, balances in another, and somewhere a line reads balances[i] -= amount with nothing but an int tying the two together. Swap one index and money quietly disappears. That is the failure mode object orientation exists to prevent: not "model the real world", but make illegal states unrepresentable and illegal operations unexpressible.

Java's answer is a class — a single declaration that bundles state (fields) with the operations that know how to keep that state valid (methods), then makes the bundle the only route to the state. A deposit() method can refuse a negative amount; a bare long cannot. And a class compiles once into a .class file — a description sitting on disk — while an object is a run-time allocation on the heap. One BankAccount description; potentially millions of distinct accounts.

Blueprint vs allocation

Here is a class that could not be simpler and yet already carries a real invariant: an account always has an owner, and its balance never goes negative or moves by a non-positive amount. Note the field types — long for money, never double, because binary floating point cannot represent 0.10 exactly and auditors notice:

BankAccount.java
public class BankAccount {
    private final String owner;      // set once, at construction
    private long balanceCents;  // long, not double: money is not a float

    public BankAccount(String owner, long opening) {
        if (owner == null || owner.isBlank())
            throw new IllegalArgumentException("owner required");
        this.owner = owner;    // 'this' = this object's copy of the field
        this.balanceCents = opening;
    }

    public void deposit(long cents) {
        if (cents <= 0)
            throw new IllegalArgumentException("cents must be > 0");
        balanceCents += cents;
    }

    public void withdraw(long cents) {
        if (cents > balanceCents)
            throw new IllegalStateException("overdrawn");
        balanceCents -= cents;
    }

    public long balance() { return balanceCents; }
}

new BankAccount("Ashton", 10_000) is where the description becomes a thing. The new operator is four steps, and knowing them explains half the "gotchas" people file under Java:

1 · allocate & zero The JVM reserves heap space for the whole object — superclass fields included — and sets every field to a language-defined default: 0, 0.0, false, null. For a moment the object exists with none of your invariants intact.
→
2 · initialisers Instance field initialisers and { ... } blocks run in source order, parent first (via its own constructor). This is where private List<X> xs = new ArrayList<>(); happens.
→
3 · constructor body Your code runs with this fully wired. It is the only step that can validate arguments and refuse to hand back an object at all — which is why constructors exist rather than plain factory methods alone.
→
4 · return the reference new is an expression; its value is a reference to the finished object. From here on, only methods you exposed can touch the state.

Static initialisation sits outside this diagram: the first time anything touches the class (a new, a static field read, a static method call), the class's own static fields and static { } blocks run once, before any object exists.

Constructors, chaining, and initialisation order

A constructor has the same name as the class and no return type. Java gives you a free one: if you declare no constructors at all, the compiler writes a public no-arg constructor for you. Declare a single constructor of your own and the free one disappears instantly — there is no way to get it back except by writing it. That is deliberate: a class with a required field should not be constructible without it.

Two constructors are allowed to share work through chaining: this(...) delegates to another constructor in the same class, and super(...) delegates to the parent. Both must be the first statement of the constructor — the compiler enforces it, because the object has to reach a fully-initialised state exactly once, along exactly one path.

⚠️ The exact initialisation order (memorise this once)

1. Static fields and static { } blocks of the class — superclass first — run once per JVM, on first use. 2. Per object: the parent's instance initialisers, then the parent's constructor body, then this class's instance initialisers and field defaults, then this constructor body.

Field initialisers are compiled into the constructor at the top of the this(...) chain — the one that calls super(...) — so no matter how many constructors you chain through, they run exactly once, ahead of that final body.

Encapsulation: getters, setters and the honest middle

Encapsulation is not "make everything private and add a getter" — that just moves the coupling one door over. The point is that the class owns its invariants. Below the line, code can corrupt state; above it, it can only ask for behaviour.

✓ A getter is nearly always fine
  • It reveals state without offering a way to corrupt it
  • Prefer account.balance() over account.getBalance() — Java has no property syntax, so drop the get
  • Return immutable types (List.copyOf, Instant) or you have merely moved the leak
✓ A setter is justified only when…
  • The state genuinely changes over the object's life and
  • It must be validated or coordinated with other fields
  • A named command would be a lie — setPaid(true) vs invoice.markPaid(clock.instant())

If your setter body is literally this.x = x;, delete it: the constructor already did that job, and a public setter turns every invariant you wrote into a suggestion. Prefer commands over setters — transferTo(other, cents), close(), markPaid() — because a named operation can maintain two fields at once while a setter never can.

static: the half that isn't about objects

Every instance method secretly receives the receiver as its first parameter — deposit(BankAccount this, long cents) — which the JVM pushes on the stack before the call. static means "no hidden this parameter", and every other consequence follows: a static method cannot read an instance field, an instance method can freely use both, and a static field is one copy shared by all instances rather than one copy per object.

🔢

static field

One copy, living on the class, shared by every instance. Use it for values that are genuinely per-class — a counter, a cache, a private static final constant table — never for per-object state.

⚙️

static method

Behaviour with no receiver: Math.max, Integer.parseInt, List.of. It belongs to the class because it doesn't need any object's state — the classic sign you're writing a utility, not a domain type.

🧱

static { } block

Initialisation too complex for an assignment: build a lookup table, System.loadLibrary, seed a cache. Runs once, on first use of the class, in the order written.

    private final int id;           // one per object

        this.id = ++instances;      // 1, 2, 3 … for this JVM run

🛑 The static-initialiser trap

Static initialisers run in textical order, exactly once, at class initialisation — not at class loading, and not on your schedule. If static int CACHE_SIZE = table.length; is written above static final int[] table = buildTable();, it silently reads 0 with no warning and no error. Worse: class initialisation is guarded by a JVM-wide lock, so a slow static { } (network call, file scan, native library) blocks every thread that touches the class, and a static block that re-enters its own class sees half-initialised values.

Identity: ==, equals() and the classic trap

These three do three different jobs, and confusing the first two is the single most common Java bug that passes local testing:

❌ == — identity (primitives: value) 
Integer a = 128, b = 128;
System.out.println(a == b);   // false — two objects

Integer c = 100, d = 100;
System.out.println(c == d);   // true — Integer.valueOf
                              // caches only −128..127

On references, == asks "same object in the heap?". The Integer cache makes it pass for small numbers and fail for large ones — a bug that survives every test written with fixture data.

✅ .equals() — value comparison 
Integer a = 128, b = 128;
System.out.println(a.equals(b));   // true — contents match

String s = new String("hi");
String t = new String("hi");
System.out.println(s.equals(t));   // true

Values compare with .equals(), always. Note the second trap: two separately-built Strings are equal but not identical — interning is an optimisation, never a semantics.

⚠️ Overriding equals without hashCode is a silent corruption

Put two equal objects in a HashSet with mismatched hash codes and the set will happily hold both — lookups then fail in one direction only. The contract: equal objects must produce equal hash codes, unequal ones should spread. The two methods are a pair; overriding one is a bug. (Kotlin sidesteps the whole trap: == there calls equals() with a null check, and === is Java's ==.)

BankAccount.java — the works
@Override
public boolean equals(Object o) {
    if (this == o) return true;         // same object: cheap win
    if (!(o instanceof BankAccount other))   // Java 16 pattern matching
        return false;
    return balanceCents == other.balanceCents
        && owner.equals(other.owner);
}

@Override
public int hashCode() {
    return Objects.hash(owner, balanceCents);       // never hand-roll badly
}

@Override
public String toString() {
    return "BankAccount[owner=" + owner
         + ", balanceCents=" + balanceCents + "]";
}
🧠 The equals contract, in five lines
  • Reflexive — x.equals(x) is true.
  • Symmetric — x.equals(y) iff y.equals(x); asymmetric implementations break HashSet in ways that depend on insertion order.
  • Transitive — if A=B and B=C then A=C; impossible if you compare a superclass field one way and a subclass field another.
  • Consistent — no field used in equals may ever change, or the object cannot live in a hash collection.
  • Never null — x.equals(null) returns false, never throws.
  • hashCode follows — equal ⇒ equal hashes. Objects.hash allocates an array; on hot paths write 31 * … by hand (the JIT turns 31*x into a shift-and-subtract).

System.out.println(someObject) does not print gibberish by accident: println calls String.valueOf, which calls someObject.toString(). The default implementation returns BankAccount@1c2b33d — class name plus the JVM's identity hash, not a memory address. Overriding toString() turns every log line, debugger view and assertion message into a diagnostic for free.

Records and immutability

If a class exists only to carry data — no invariants beyond "not null", no behaviour beyond accessors — a record replaces it in one line and writes equals, hashCode, toString and accessors for you. Chapter 07 goes deep; here is the immutability recipe that records encode by hand:

Invoice.java
public final class Invoice {       // final: no subclass can weaken it
    private final String id;         // final: set once, in the ctor
    private final List<Line> lines;

    public Invoice(String id, List<Line> lines) {
        this.id = Objects.requireNonNull(id);
        this.lines = List.copyOf(lines);  // defensive COPY at the boundary
    }

    public List<Line> lines() {
        return lines;           // already immutable — safe to share
    }
}

Two moves make this genuinely immutable: final fields stop reassignment, and List.copyOf stops the caller from holding a handle into your internals. Without the copy, a getLines().add(...) from anywhere in the program mutates your invoice behind your back — Collections.unmodifiableList alone only wraps the view, so an attacker with the original reference still writes through it.

💡 When a record beats a class
  • Yes: value objects, DTOs, exceptions' payloads, results of a parse, anything you would have given four getters and an equals.
  • No: anything with a mutable field, a no-arg constructor, a superclass, or identity that matters across time.
  • Rule: if you can't name an invariant that a constructor must defend, it's a record.

Chapter 06

Inheritance, interfaces & polymorphism

Java gives you exactly one class slot and unlimited interface slots — inherit implementation from a single parent, compose contracts from as many types as you like — and the language's costliest design bugs come from reaching for the first tool when the second one was built for the job.

Start with the problem polymorphism actually solves. You keep Circle, Square and Triangle in one list, and every renderer, exporter and hit-tester needs to do something with them. Without a shared supertype you write if (x instanceof Circle) … else if (x instanceof Square) … in every method, and adding a fourth shape means grepping for every chain you ever wrote. One supertype with an abstract draw() moves that work to the compiler: implement it once per shape, call it anywhere, and a missing implementation is a build error instead of a null in production.

extends buys you that and free implementation reuse — which is exactly the trap. Inheritance is handed two jobs at once: subtyping (a Circle is a Shape, so a Shape reference may point at it) and code reuse (borrow the parent's methods). The first is a sound, powerful type-system feature. The second is a coupling decision you cannot undo. Java's answer is to give reuse its own mechanism — interfaces with default methods, sealed families, and delegation — so that you choose deliberately instead of by default.

extends: inheriting a whole parent object

A subclass object physically contains the superclass's fields — including its private ones. The storage is there; the name simply isn't accessible from the subclass. That containment is why the constructor chain runs parent-first: the parent half of the object must satisfy its own invariants before any child code can run against it. Java enforces this syntactically — super(...) must be the first statement of every constructor, and if the parent declares no no-arg constructor, javac will not invent one for you; you must write the call yourself.

Shapes.java
abstract class Shape {
    private final String name;          // parent state, private to Shape

    protected Shape(String name) { this.name = name; }

    abstract void draw();          // no body — subclasses must supply one

    @Override public String toString() { return name; }
}

final class Circle extends Shape {
    private final double r;

    Circle(double r) { super("circle"); this.r = r; }  // super(...) FIRST

    @Override void draw() { System.out.println("circle r=" + r); }
}

class Paint {
    public static void main(String[] args) {
        Shape[] shapes = { new Circle(1), new Square(2) };  // many types
        for (Shape s : shapes) s.draw();   // dispatch on RUNTIME type
    }
}

That loop is polymorphism in one line: the reference s is a Shape at compile time, and each element is a Circle or Square at run time. The JVM executes it with invokevirtual, which looks the method up in the object's own method table on every call — so s.draw() resolves to the right body without the caller knowing or caring which body it is.

🧠 Why you can't write new Shape()

The compiler answers with one line: error: Shape is abstract; cannot be instantiated. It isn't pedantry — new must produce an object whose every method-table slot is filled, and an abstract class deliberately has empty ones. An abstract class is a half-finished template: useful as a base, meaningless on its own. You can still hold one as a reference type, and the classic way is an anonymous subclass that finishes it on the spot: Shape s = new Shape() { void draw() { … } };

Overriding — and the three lookalikes that aren't

@Override is not documentation, it's a type-check. Write it every single time. Without it, a typo like equals(MyAccount other) doesn't override anything — it quietly declares a brand-new overload, your equals contract silently stops applying, and HashSet starts misbehaving weeks later. With the annotation, the same typo is a compile error on the spot.

🎯

Signature matches exactly

Same name, same parameter types. The return type may stay the same or be narrowed — a covariant return like Circle self() overriding Shape self() is legal, because callers expecting a Shape still get one.

🔓

Visibility may only widen

protected → public is fine. public → protected is a compile error: you'd be removing a method that every existing caller of the parent can already reach.

🎯

Exceptions may only narrow

An override may throw the same checked exceptions or narrower subtypes of them — never broader. Otherwise code written against the parent could suddenly fail with something it never handled.

🚫

Not every method participates

private methods are invisible to subclasses and never overridden. static methods are hidden, not overridden — the JVM binds them with invokestatic at compile time. final refuses outright.

⚠️ Overloading is not overriding

Overloading means several methods with different parameters — picked statically, from the reference type, before anything runs. Overriding means the same signature in a subclass — picked dynamically, from the object's actual class. Declare draw(double r) in the child while the parent has draw(int r) and you have overloaded, not overridden: a call through a Shape reference still runs the parent's method, and nobody gets an error. This is why @Override is non-negotiable — it is the compiler telling you which of the two you actually wrote.

One more rule with teeth: package-private methods only override inside the same package. A subclass in another package that redeclares one is declaring a new method, and the parent's own call sites will still run the parent's copy. A quiet source of "why is my logging not firing?" bugs across jar boundaries.

The Liskov trap: Square cannot extend Rectangle

Liskov's Substitution Principle says a subtype must be usable everywhere its supertype is promised, with the same observable guarantees. It sounds abstract until you watch it fail with numbers:

Lsp.java
class Rectangle {
    private int w, h;
    Rectangle(int w, int h) { this.w = w; this.h = h; }
    void setSize(int w, int h) { this.w = w; this.h = h; }
    int area() { return w * h; }
}

final class Square extends Rectangle {        // compiles. Breaks the world.
    Square(int side) { super(side, side); }
    @Override void setSize(int w, int h) {   // a square can't move one side
        super.setSize(Math.max(w, h), Math.max(w, h));
    }
}

static void widen(Rectangle r) {
    r.setSize(5, 3);
    assert r.area() == 15;  // every caller of Rectangle relies on this
}

// widen(new Rectangle(2, 2))  → 15  ✅
// widen(new Square(2))        → 25  ❌ and it changes with argument order

The code compiles, the hierarchy reads beautifully, and the assertion now fails depending on which concrete class was passed in. The flaw isn't Square — it's that Rectangle promised "set the sides independently, then ask me the area" and a square cannot honour that promise while remaining a square. Two fixes, both good: make both types immutable values with no setters at all (then the impossible operation simply doesn't exist), or model the shared contract by capability — Shape { int area(); void draw(); } — rather than by data layout.

🚫 Myth: "Inheritance is for code reuse"

Inheritance is for subtyping. Reuse is a side effect, and it's the side effect that bites: every protected method and every state field you inherit becomes permanent API you never wrote and can never shrink, your subclass is coupled to the parent's bugs and its schedule, and one parent change ripples through every child. When you find yourself inheriting purely to borrow twenty lines of code, that's a signal — move the twenty lines into a small class and hold one. Prefer composition over inheritance is the oldest design rule in Java literature, and it's still the one that ages best.

Abstract classes vs interfaces

Both declare void draw() without writing it. The differences are all about what else each can carry:

Rule of thumb: interfaces for what a type can do, abstract classes for how much of its implementation you're willing to inherit. Public library code (Spring's JpaRepository, JDBC's ResultSet) almost always hands you an interface plus a tiny abstract helper.

Interfaces became a code-sharing tool in Java 8. default methods give a body inside the interface, static methods on the interface are utility functions that don't pollute implementations (Java 8), and private interface methods let you extract shared helpers that callers never see (Java 9+). This exists because interfaces must be evolvable: adding removeIf and stream() to Collection would have broken every implementation on Earth if each one had to write the method itself.

Hello.java
interface Named {
    default String hello() { return "hi " + name(); }
    String name();
}

interface Loud {
    default String hello() { return "HEY " + name(); }   // the diamond
    String name();
}

// class Person implements Named, Loud   ❌ compile error:
//   types Named and Loud are unrelated; class must override hello()

class Employee implements Named, Loud {            // ✅ resolve it yourself
    public String name() { return "Ashton"; }
    @Override public String hello() {
        return Named.super.hello() + " (" + name() + ")";  // explicit parent
    }
}
🧠 How the diamond resolves — in this order
  • 1. The class's own method always wins. A concrete hello() in Employee beats any interface default.
  • 2. The most specific interface wins. If Loud extends Named, Loud's default beats Named's — same rule as class overriding.
  • 3. Unrelated defaults? The compiler refuses and demands an explicit override, resolved with Named.super.hello(). No run-time ambiguity is ever possible.
  • The class's abstract methods beat defaults too — you can always be forced to write a method, never forced to accept someone else's.

This is why multiple interface inheritance is uncontroversial while multiple class inheritance is banned. A class can be Comparable<Order>, Runnable, Serializable and AutoCloseable simultaneously — four independent capabilities, each with its own contract, none dragging in state. Single class inheritance plus multiple interface inheritance is the compromise that keeps the object layout predictable while letting you compose behaviour freely.

Sealed types: a set the compiler can count

Open inheritance has a blind spot: a switch over a hierarchy can never be proven complete, because tomorrow someone adds a subclass in another jar. Java 17 closed that gap. A sealed class names its permitted subtypes, and the compiler can finally enumerate them:

Shape.java
public sealed interface Shape
        permits Circle, Rect, Triangle {}

public record Circle(double r) implements Shape {}      // implicitly final
public record Rect(double w, double h) implements Shape {}
public record Triangle(double b, double h) implements Shape {}

static double area(Shape s) {
    return switch (s) {
        case Circle c   -> Math.PI * c.r() * c.r();
        case Rect r     -> r.w() * r.h();
        case Triangle t -> 0.5 * t.b() * t.h();
        // no 'default' — the compiler PROVED all three of them
    };
}

Composition, with a concrete refactor

Here is inheritance doing what it's usually sold as, and the bill arriving on the second requirement. You need card and PayPal payments; then fraud checks; then retries:

The Kotlin counterpart

Kotlin's biggest single difference from Java here: classes are final by default.   • One class, many interfaces. extends for a stable is-a family; implements for capabilities you compose.
  • super(...) is always the first statement; subclass fields initialise after the parent is fully built.
  • Annotate every override with @Override — it converts a silent overload into a compile error.
  • private, static and final members are not polymorphic; visibility may widen, exceptions may only narrow.

Designing data: enums, records & builders

Most Java code is either carrying data around or describing a fixed set of things. Java has first-class syntax for both — most teams simply don't use it.

An OO design problem usually splits into two halves: things with behaviour and identity (classes), and things that are just values (records). Confusing the two is where most modeling pain starts.

🏷️

Enum

A fixed, named set with real methods. Not "an int with a name" — it's a class with exactly N instances.

📦

Record

An immutable value carrier with generated equality. For DTOs, money, coordinates, events.

🏗️

For classes with many optional fields where a telescoping constructor becomes unreadable.

Enums are full classes

Chapter 08

Generics & variance

Generics let one ArrayList serve Strings, Integers and your own classes while the compiler proves at every line that you never mix them up — and the single fact that Java implements them by erasure explains every strange restriction you are about to meet.

Before Java 5 shipped in 2004, a collection was a bag of Object. You could put anything in, you got Object back out, and you cast it to whatever you believed was inside. The compiler could not check that belief, so the mistake did not surface as a compile error — it surfaced as a ClassCastException three methods away from the line that caused it, in production, at 2 a.m.

Generics add one piece of information — "this list holds Strings" — and the compiler uses it to type-check every add and every get. Nothing about the runtime changes. That gap between "checked at compile time" and "gone at runtime" is the whole story of this chapter, and it is why Java's generics look slightly dumber than C++ templates and slightly dumber than Kotlin's.

❌ Pre-generics — raw collections, errors at runtime 
List names = new ArrayList();   // raw type: List of Object
names.add("Ada");
names.add(42);                  // compiles — nothing stops you
String s = (String) names.get(1);
System.out.println(s.length()); // 💥 ClassCastException: Integer

The failure is four lines from the mistake that caused it. Every read is an unchecked cast the compiler signs off on blindly.

✅ Java 5+ — generics, errors at compile time 
List<String> names = new ArrayList<>();
names.add("Ada");
names.add(42);                  // ❌ Integer is not a String
String s = names.get(1);        // no cast — already known
System.out.println(s.length()); // ✅

Identical bytecode discipline, one line of type information, and an entire category of bug becomes a red squiggle in your editor.

Generic classes, interfaces and methods

A type parameter is a placeholder declared in angle brackets after the class or method name. Conventions are strong and worth obeying — every Java dev reads K/V as map key/value without thinking:

Generics.java
import java.io.Serializable;
import java.util.List;

public class Generics {
    // A generic CLASS: T is a type PARAMETER, resolved at each use site
    public static class Box<T> {
        private T value;
        public void set(T value) { this.value = value; }
        public T get()           { return value; }
    }

    // Generic METHOD: the <T> lives on the method, and inference finds it
    public static <T extends Comparable<T>> T max(List<T> list) {
        T best = list.get(0);
        for (T t : list) {
            if (t.compareTo(best) > 0) best = t;
        }
        return best;
    }

    // Multiple bounds: at most ONE class, then interfaces, joined by &
    // (the class goes first because it is the most restrictive slot)
    public static <T extends Number & Comparable<T> & Serializable>
    void export(T t) {
        System.out.println(t + " is comparable to itself: "
                + (t.compareTo(t) == 0));
    }

    public static void main(String[] args) {
        Box<String> b = new Box<>();   // diamond: infer <String> from the left
        b.set("hello");

        List<Integer> nums = List.of(3, 9, 4);
        System.out.println(max(nums)); // 9 — T inferred as Integer
        export(42);                    // T inferred as Integer
    }
}

The bound <T extends Comparable<T>> is the workhorse constraint: "T must be able to compare itself to another T." It is what makes max type-safe rather than a cast-fest, and it is exactly the bound Collections.sort puts on its argument. A bound is a promise the compiler enforces — pass a type that isn't Comparable and you get a compile error at the call site, not a ClassCastException.

🧠 Type inference did most of the work in that file

You wrote new Box<>() and max(nums), never spelling out Box<String> or <Integer>. Java 7 added the diamond; Java 8 massively improved target typing, so the compiler works backwards from the assignment, the parameter or the return type to solve for the type arguments. Chained fluent calls like Collectors.toList() inside stream.collect(...) rely on this — you only ever write the types at the outermost edge.

Type erasure: the one fact that explains everything

Here is the single most important thing to know about Java generics: type arguments exist only at compile time. The compiler checks your code, then throws the type arguments away before producing bytecode. A List<String> and a List<Integer> are, at runtime, the same class java.util.ArrayList. This is type erasure, and it exists for one reason: Java 5 had to stay binary-compatible with the mountain of pre-generics code already deployed. Erasure let ArrayList gain type safety without gaining a second, incompatible runtime identity.

🛑 Erasure: three things you simply cannot write

Because the type parameter is gone at runtime, none of these compile:

1. new T[] — the JVM must know an array's component type to allocate it, and T is not a runtime type. 2. instanceof List<String> — there is nothing to test; o instanceof List<> (Java 9+) is the most you get, and it only proves the raw class. 3. static T members — static fields and methods belong to the class, not an instance, and a class has exactly one set of erased fields, so T is not in scope in a static context.

Erased.java
public class Erased<T> {
    // T[] make()          { return new T[10]; }   // ❌ generic array creation
    // static T first(...) { ... }                 // ❌ static cannot see T
    // boolean bad(Object o) {
    //     return o instanceof List<String>;       // ❌ illegal generic type
    // }

    public String getAndCast() {

Unchecked warnings and when to shut them up

Some code is genuinely type-safe but unprovable to the compiler — anything touching Class<T>, reflection, or a raw legacy API. That produces an unchecked conversion warning. The discipline: verify the safety by hand, then annotate the exact method, never the whole file, and say why.

Unchecked.java
public class Unchecked {
    // Raw type returned by a pre-generics library
    @SuppressWarnings("unchecked")  // we promise the runtime list is List<T>
    static <T> List<T> legacyQuery(Class<T> type) {
        List raw = new java.util.ArrayList();   // raw — no type info
        raw.add("built for " + type.getSimpleName());
        return raw;
    }

    // SAFER alternative when you have the Class token: a checked copy
    static <T> List<T> checkedCopy(Class<T> type, List<?> in) {
        List<T> out = new java.util.ArrayList<>();
        for (Object o : in) {
            if (!type.isInstance(o)) {
                throw new ClassCastException(
                        "expected " + type.getName() + ", got " + o.getClass());
            }
            out.add(type.cast(o));   // the cast happens HERE, with a real check
        }
        return out;
    }
}
⚠️ @SuppressWarnings("unchecked") is a loaded gun

It does not remove the risk, it removes the warning about the risk. Erasure means a List<String> and a List<Integer> are the same object at runtime, so a single leaked raw reference can put an Integer into a list of Strings that the compiler believes is pure — heap pollution. The failure then appears, via a bridge method, far from the leak. Keep the annotation narrow (one method), add a comment stating exactly why it's safe, and prefer a checked copy using type.cast(o) when the code path is cold.

Variance: arrays lie, generics don't

Variance is the question "if Integer is a Number, is a list of Integers a list of Numbers?" Java gives two different answers, and the inconsistency is deliberate.

Arrays are covariant — Integer[] is a subtype of Number[], and it compiles. Generics are invariant — List<Integer> is not a List<Number>, and it doesn't compile. Arrays made that concession in 1.0 to let polymorphism work with collections of primitives-era code, and the JVM has paid for it ever since:

ArrayStore.java
public class ArrayStore {
    public static void main(String[] args) {
        // Covariance: an Integer[] IS a Number[] as far as javac is concerned
        Number[] nums = new Integer[3];
        nums[0] = 10;                     // ✅ fine

        // ...and here is the hole. The compiler accepted this because
        // Integer is a Number. The JVM remembers the real component type
        // and refuses at RUNTIME:
        nums[1] = 3.14;                   // 💥 ArrayStoreException
        // java.lang.ArrayStoreException: java.lang.Double

        // Generics close this hole by refusing to compile it at all:
        // List<Number> l = new ArrayList<Integer>();  // ❌ incompatible types
    }
}
🚫 Myth: "generics are just syntactic sugar for Object"

Erasure makes the runtime representation identical to raw Object, but the compile-time effect is enormous: generics turn a whole family of runtime crashes into build failures, let the compiler infer and check method signatures, and enable the wildcard rules below. The cost is real too — you can't overload on type argument, can't construct T, and can't test against a concrete argument type. C# picked reified generics instead and got those abilities at the price of runtime complexity Java chose never to pay.

Wildcards: ? extends, ? super and PECS

Invariance would be unbearable if there were no escape hatch. There is one: use-site wildcards, which express variance at the point of use rather than at the declaration.

DeclarationMeaningYou may readYou may write
List<? extends Number>a list of Number or any subtypeas Numbernothing but null
List<? super Number>a list of Number or any supertypeas ObjectNumber and subtypes

The mnemonic, straight from Joshua Bloch: PECS — Producer Extends, Consumer Super. If the collection produces values to you, use extends. If it consumes values from you, use super.
Pecs.java
import java.util.ArrayList;
import java.util.List;

public class Pecs {
    // CONSUMER: we only put Numbers in → "? super Number" (PECS)
    static void fill(List<? super Number> sink, Number... values) {
        for (Number n : values) sink.add(n);   // ✅ adding Number is safe
    }

    // PRODUCOR: we only take Numbers out → "? extends Number" (PECS)
    static double sum(Collection<? extends Number> src) {
        double total = 0;
        for (Number n : src) total += n.doubleValue();  // ✅ reads as Number
        return total;
    }

    public static void main(String[] args) {
        List<Number> nums = new ArrayList<>();
        List<Object> any  = new ArrayList<>();
        fill(nums, 1, 2.5, 3L);   // ✅ List<Number> is within "? super Number"
        fill(any,  1, 2.5, 3L);   // ✅ List<Object> too — Object is a supertype

        // List<Integer> ints = ...; fill(ints, ...);   // ❌ Integer is a SUBtype
        //                                            //    you'd get Integers,
        //                                            //    not Numbers. Correctly
        //                                            //    rejected.

        System.out.println(sum(nums));   // 6.5
        System.out.println(sum(any));    // 6.5 — same call, wider argument
    }
}
💡 Why List<Object> cannot hold a List<String>

If it could, the compiler would have to let you call add(Integer.valueOf(1)) on that List<Object> — and that list is really a List<String> somewhere else in your program, so the next get returns an Integer to code expecting a String. Erasure means the JVM could not stop it. Invariance stops it at compile time instead. If you only need to read Strings through an Object-typed reference, write List<? extends Object> — which is what Iterable<? extends Object> means, and why the for-each loop works on any collection at all.

Kotlin's answer: variance on the declaration

Kotlin has the same erasure — it runs on the same JVM — but it moves the variance decision to the declaration site, with out and in. Declare it once on the class and every use site inherits it, so ordinary Kotlin code has no wildcards at all.

Variance.kt
// out T = covariant ("produce only"). in T = contravariant ("consume only").
interface Source<out T> { fun next(): T }        // T in out position ✅
interface Sink<in T>   { fun put(t: T) }         // T in in position  ✅
// interface Bad<out T> { fun put(t: T) }        // ❌ out-projected type
//                                                 //    used in in position

fun main() {
    val names: List<String> = listOf("Ada", "Grace")

    // Kotlin's List IS declared `List<out E>` — so covariance is free:
    val asAny: List<Any> = names          // ✅ no wildcard, no ceremony
    val first: Any = asAny[0]

    // Mutable lists stay invariant, exactly like Java:
    // val w: MutableList<Any> = mutableListOf<String>()  // ❌ type mismatch

    // Star projection: "I know the shape, not the argument"
    val star: List<*> = names
    println("${star.size} items, first = ${star[0]}")   // element type = Any?

    // Reified type parameters — the thing Java genuinely cannot do:
    val mixed: List<Any> = listOf(1, "two", 3.0)
    println(mixed.filterIsInstance<Int>())   // [1] — survives erasure!
    println(isA<String>(mixed[0]))           // false
}

// `inline` + `reified` copies the body into the caller with T substituted,
// so `is T` and `::class` work. Only possible in functions, never classes.
inline fun <reified T> isA(value: Any): Boolean = value is T

Reification is the one place Kotlin is strictly ahead. Because the function is inline, the compiler pastes its body at each call site with the type argument written in concretely — value is Int — so the check is real. Java cannot do this for classes or methods generally; its only equivalent is passing a Class<T> token and calling isInstance on it manually, which is precisely why filterIsInstance exists as a Kotlin library function and not a Java one.

✅ What to remember
  • Generics move ClassCastException to compile time — that's the entire benefit.
  • Type parameters are conventions: T type, E element, K/V key/value.
  • Bounds: <T extends Comparable<T>>; multiple bounds join with &, class first.
  • Erasure: type arguments vanish at runtime → no new T[], no instanceof List<String>, no static T.
  • Watch a bridge method with javap -p — it's the erased cast made visible.
  • Arrays are covariant and can throw ArrayStoreException; generics are invariant and can't.
  • Use PECS: producer extends, consumer super.
  • Kotlin declares variance once with out/in, and inline fun + reified beats erasure where Java cannot.

Streams: declaring what, not how

A stream is a lazy pipeline over a source. Nothing runs until a terminal operation — which is why filter before map matters and why side effects inside a stream are a design smell.

streams.java
record User(String name, int age, String dept) {}

List<User> users = List.of(
    new User("Ada", 36, "eng"),
    new User("Grace", 45, "eng"),
    new User("Alan", 41, "research"),
    new User("Katherine", 34, "ops"));

// Pipeline: filter → map → sort → collect
List<String> engOver40 = users.stream()
    .filter(u -> u.dept().equals("eng"))
    .filter(u -> u.age() > 40)
    .map(User::name)
    .sorted()
    .toList();                          // [Grace]

// Grouping — the killer feature over imperative loops
Map<String, List<User>> byDept = users.stream()
    .collect(Collectors.groupingBy(User::dept));

// Counts, sums, averages in one expression
Map<String, Long> headcount = users.stream()
    .collect(Collectors.groupingBy(User::dept, Collectors.counting()));

OptionalDouble avg = users.stream().mapToInt(User::age).average();

// Reduce to a single value
String all = users.stream().map(User::name).collect(Collectors.joining(", "));

// Short-circuiting
users.stream().filter(u -> u.age() > 40).findFirst();
users.stream().anyMatch(u -> u.dept().equals("ops"));
🪟

Intermediate ops are lazy

filter, map, sorted build a plan. Only collect, count, findFirst actually pull data through.

🧮

Short circuits

anyMatch, findFirst and limit stop early — a stream over 10M rows can touch 3.

🌲

No side effects

Stateful lambdas break under parallelism. Return values from the lambda; don't mutate captured variables.

🧠 Stream vs plain loop

A stream wins when the pipeline is genuinely declarative — filter, transform, group, join. A plain loop wins when you need early break, multiple interacting accumulators, or an if/else that doesn't map to a predicate. Reaching for peek() three times means you wanted a loop.

✅ What to remember
  • Program to interfaces: List, Map, Set — never ArrayList in a signature.
  • ArrayList + HashMap are the defaults — deviate only with a measured reason.
  • ArrayDeque beats LinkedList for both stacks and queues.
  • removeIf instead of mutating during iteration.
  • Streams are for pipelines; loops are for control flow. Don't force either.

Regex lives in java.util.regex: a Pattern is compiled and reusable, a Matcher walks one input. Compiling inside a loop is a classic hot-path mistake.

Regex.java
import java.util.regex.*;

public class Regex {
    // Compile ONCE as a static field
    private static final Pattern LOG = Pattern.compile(
        "^\\s*(?<time>\\d{2}:\\d{2}:\\d{2})\\s+"
      + "(?<level>INFO|WARN|ERROR)\\s+"
      + "(?<msg>.*)$");

    public static void main(String[] args) {
        String line = "14:03:22 ERROR database timed out";

        Matcher m = LOG.matcher(line);
        if (m.matches()) {
            System.out.println(m.group("level"));  // ERROR — named groups
            System.out.println(m.group("msg"));    // database timed out
        }

        // find() searches anywhere; matches() requires the WHOLE string
        System.out.println(Pattern.compile("\\d+").matcher("a12b345")
                                  .find());                    // true

        // Replacing with a lambda — captured text flows back in
        String masked = line.replaceAll(
            Pattern.quote("database"), "REDACTED");

        // Splitting with a limit
        String[] parts = "a,b,,c".split(",", -1);   // [a, b, , c]

        // Quick validation without Pattern boilerplate
        System.out.println("ada@example.com".matches("[\\w.]+@[\\w.]+")); // true
    }
}

Exceptions & the error-handling model

Java's exceptions are checked at compile time — a design no mainstream language copied, and the most argued-about feature in the language. Understand why it exists before you work around it.

Every throwable descends from Throwable: Error for things you shouldn't catch (out of memory, stack overflow) and Exception for things programs are expected to handle. RuntimeException and its children are unchecked — the compiler doesn't force you to declare or catch them.

🔴

Checked

Subclass of Exception, not RuntimeException. Must be declared in throws or caught. Compiler enforces it.

🟡

Unchecked

RuntimeException and subclasses. No declaration required — NullPointerException, IllegalArgumentException.

⚫

Error

JVM-level failures. Let them propagate — catching OutOfMemoryError rarely helps.

Throwing.java
public class Throwing {

    // Checked: the signature forces callers to deal with it
    static int parseAge(String raw) throws NumberFormatException {
        if (raw == null || raw.isBlank())
            throw new NumberFormatException("blank input");
        return Integer.parseInt(raw);   // throws on garbage
    }

    // Unchecked: no declaration — signals a programming mistake
    static String lookup(String[] table, int i) {
        if (i < 0 || i >= table.length)
            throw new IndexOutOfBoundsException("index " + i + " out of bounds");
        return table[i];
    }

    // Custom checked exception: real domain failure
    public static class InsufficientFunds extends Exception {
        private final long shortfall;
        public InsufficientFunds(long shortfall) {
            super("short by " + shortfall + " cents");
            this.shortfall = shortfall;
        }
        public long shortfall() { return shortfall; }
    }

    static void withdraw(long balance, long amount) throws InsufficientFunds {
        if (amount > balance) throw new InsufficientFunds(amount - balance);
    }
}
⚠️ Never catch-and-swallow

catch (Exception e) {} deletes the failure and leaves you debugging a symptom three layers away. If you truly cannot handle it, at minimum log with the stack trace — e.printStackTrace() beats silence.

❌ The four sins 
try { risky(); }
catch (Exception e) {}              // swallow

try { risky(); }
catch (Exception e) { return; }     // hide it, plus no context

try { risky(); }
catch (Exception e) {
    throw new RuntimeException(e);  // loses the call site semantics
}

try { risky(); }
catch (IOException e) { throw e; }  // pointless — declare it instead

Each one makes the original failure harder to find. Rethrow e itself when you can't add value.

✅ Catch only what you can handle 
try {
    send(order);
} catch (ConnectException e) {
    // This layer knows the retry policy — handle it here
    log.warn("mail down, queueing {}", order.id());
    outbox.enqueue(order);
}

// Let everything else propagate
// Never catch Exception or Throwable broadly in library code

Catch at the layer that has enough information to choose a different path. Otherwise, let it travel up.

✅ Designing an exception worth throwing
  • Name it after the problem: InsufficientFunds, not MyException.
  • Carry the data needed to recover — the ID, the offending value, the line number.
  • Message for humans, fields for code. Never parse a message.
  • Make it checked only if callers can plausibly handle it. Most domain failures are unchecked.
  • Chain the cause when wrapping: new X(msg, e).

Functional Java: lambdas, Optional & method refs

Java 8 bolted functional programming onto an object-oriented language. The result isn't Haskell — it's a pragmatic set of tools for passing behaviour instead of objects.

A lambda is an anonymous function: no name, no class file you wrote, and it can be stored in a variable, passed to a method, and returned. The type it binds to is a functional interface — any interface with exactly one abstract method.

Lambdas.java
import java.util.function.*;

public class Lambdas {
    public static void main(String[] args) {
        // Explicit type — verbose, occasionally useful for clarity
        Runnable r1 = () -> System.out.println("hi");

        // Inferred — the target type gives the compiler everything it needs
        Function<String, Integer> len = s -> s.length();
        Predicate<String>           long1 = s -> s.length() > 4;
        BiFunction<Integer, Integer, Integer> add = (a, b) -> a + b;

        System.out.println(len.apply("hello"));   // 5
        System.out.println(long1.test("hi"));     // false
        System.out.println(add.apply(2, 3));      // 5

        // Blocks, when the body needs more than one expression
        Comparator<String> byLenThenAlpha = (a, b) -> {
            int d = Integer.compare(a.length(), b.length());
            return d != 0 ? d : a.compareTo(b);
        };

        // Effectively final captured variables
        String prefix = "log: ";       // cannot be reassigned after this line
        Consumer<String> out = s -> System.out.println(prefix + s);
        out.accept("started");
    }
}

🧠 Why "effectively final"?

A lambda runs later, possibly on another thread, after your method's stack frame is gone. If it captured a variable that had changed, it would read a value that no longer exists. Java freezes the capture at creation time instead — which is why you can't reassign prefix after the lambda uses it.

A Proxy creates, at runtime, an implementation of any interface that forwards every call through one handler method. This is the mechanism behind mocking frameworks and every RPC client.

Chapter 14

Threads, locks & the memory model

Concurrency is not "two things at once" — it's two threads reading and writing the same memory while the CPU interleaves them anywhere, and the JVM deciding freely when (or whether) one thread ever sees the other's writes. Locks fix the interleaving; only the Java Memory Model fixes the visibility.

Every hard concurrency bug comes from one thing: shared mutable state. Shared — two threads can see it. Mutable — someone can change it. State — it holds a value that matters later. Kill any one of the three and the bug class disappears: make it immutable (a final record), keep it confined to one thread, or share by passing messages instead of pointing both threads at the same field.

The JVM gives you real OS threads, per-object monitors, and a written specification — the Java Memory Model — that says exactly which writes a thread is obliged to observe. That specification is what everyone skips, and it's what explains why a loop spins forever on your laptop and exits instantly in CI. Chapter 15 builds pools, futures and virtual threads on top of it, so this chapter comes first.

Creating threads — and the trap in start()

A platform thread costs an OS scheduling entity plus roughly 1 MB of stack. Java gives you three ways to use one: subclass Thread, hand it a Runnable (no result), or submit a Callable (returns a value, may throw). The last two are what you actually use.

ThreadsDemo.java
import java.util.concurrent.*;
import java.util.stream.IntStream;

public class ThreadsDemo {
    public static void main(String[] args) throws Exception {
        // (1) a bare Thread wrapping a Runnable
        Thread t = new Thread(
            () -> System.out.println("hi from " + Thread.currentThread()));
        t.start();                   // NEW OS thread — this is the magic
        t.join();                    // main blocks until t is TERMINATED

        // (2) Runnable: no result. Callable: returns a value.
        Runnable job = () -> System.out.println("fire and forget");
        Callable<Integer> sum = () -> IntStream.range(0, 100).sum();

        ExecutorService pool = Executors.newFixedThreadPool(4);
        Future<Integer> f = pool.submit(sum);
        System.out.println(f.get()); // 4950 — blocks main until ready
        pool.shutdown();
    }
}
🛑 The classic bug: run() instead of start()

t.run() is an ordinary method call. It executes on your current thread, synchronously, and no second thread is ever created. The bug is silent — output still appears, logic still works, it just isn't concurrent, and any exception it throws lands in your caller. Only start() asks the OS for a thread, and each thread may be started once: a second start() throws IllegalThreadStateException.

synchronized — you lock an object, not some code

Every Java object carries an intrinsic lock (a monitor). synchronized acquires and releases it, and the JVM guarantees that only one thread may hold a given monitor at a time. Crucially, what gets locked is the object reference in the parentheses, not the block of code — so two threads entering the same method of two different instances sail straight past each other.

Counter.java
public class Counter {
    private int count;                       // guarded by `this`
    private static int instances;            // guarded by Counter.class
    private final Object gate = new Object(); // a private, dedicated lock

    public synchronized void bump() {        // (1) method → locks `this`
        count++;
    }

    public static synchronized void resetAll() {  // (2) static → locks the
        instances = 0;                            //     Class object itself
    }

    public int read() {
        synchronized (gate) {                // (3) block: you choose the
            return count;                    //     exact object to lock
        }
    }
}

Three rules keep you out of trouble. Lock the object that owns the state — a private final Object is best, because nobody outside can grab it and lock it too. Never lock on something publicly reachable (this in a library class, String.class, a boxed Integer). Monitors are also reentrant: a thread already holding a lock may re-enter code needing it, which is why a synchronized method can safely call another on itself.

The race you can reproduce: count++

count++ looks atomic and is not. It is three operations: read the field, add one to the local copy, write it back. Interleave those three steps between two threads and updates vanish — each thread reads the same stale value and both write the same result.

❌ Broken — three unsynchronised steps 
int hits = 0;          // shared field
// thread A: read 0 → add → write 1
// thread B: read 0 → add → write 1   ← A's work is gone
hits++;                // 8 threads × 1000 increments → maybe 3100

The lost update is invisible in testing and certain at scale. More threads, more cores and a slower GC all make it worse.

✅ Correct — one atomic instruction 
AtomicInteger hits = new AtomicInteger();

hits.incrementAndGet();  // read-modify-write in ONE step
int now = hits.get();    // always a value some thread really wrote

No lock is taken. The JVM emits a compare-and-set loop on a single CPU instruction.

That compare-and-set (CAS) is the whole trick of lock-free code: read the old value, compute the new one, then compareAndSet(old, new) — one lock cmpxchg instruction on x86. If another thread got there first, the CAS fails and you retry. Nothing blocks, so nothing deadlocks. And if you only ever add and only read at the end, use LongAdder: it stripes the counter across per-thread cells so contending threads stop fighting, then sums them in sum() — routinely much faster than AtomicLong under load.

⚠️ volatile is not a lock

volatile guarantees visibility and ordering — every thread reads the latest write, and no read or write may be moved across it. It guarantees nothing about atomicity: volatile int n; n++; still loses updates, because the read-modify-write is still three steps. Use it for flags, snapshots and immutable published state; use synchronized, Atomic* or a concurrent collection when a value is read, changed and written back.

The same trap hides in collections: mutating a plain ArrayList during a for-each throws ConcurrentModificationException. Across two threads it's worse — fail-fast is best-effort, so you may corrupt the list silently instead of getting an exception. Confine mutation to one thread, or use CopyOnWriteArrayList / ConcurrentHashMap from Chapter 13.

The Java Memory Model — happens-before

The JMM does not promise a write becomes visible "soon". It promises visibility when a happens-before edge connects write to read: if write A happens-before read B, B must see A's value or something later. Edges come from program order within a thread, unlocking then re-locking the same monitor, a volatile write then read, start(), and join() returning. No edge — no obligation, and your thread may legally read a stale copy from a register forever.

DirtyFlag.java
public class DirtyFlag {
    private volatile boolean running = true; // ← delete this keyword: hang
    private int port = 8080;                 // written once, before start

    public void stop() {                     // called from another thread
        running = false;
    }

    public void run() {
        while (running) {                    // re-read on every iteration
            Thread.onSpinWait();             // JDK 9+ polite yield hint
        }
        System.out.println("clean exit on " + port);
    }
}

Without volatile, the JIT may prove that run() never writes running, hoist the field into a register and turn your loop into an unconditional jump. The other thread's write lands in memory and is never read again — the method hangs forever, on one JDK build, after warm-up. That's not a JVM bug; it's correct optimisation under a model that never promised you that read.

Deadlock, livelock, starvation

Deadlock is two threads each holding what the other needs, so both sit in BLOCKED forever. It requires all four Coffman conditions to hold at once — which is good news, because breaking any single one prevents it.

🔒

1 · Mutual exclusion

Only one thread can hold a resource. Break it: use immutable state or atomics that nobody "holds".

✋

2 · Hold and wait

A thread holds lock A while waiting for B. Break it: acquire all locks up front, or none.

🚫

3 · No preemption

Nobody can take a lock away. Break it: tryLock(timeout) gives up and releases.

🔄

4 · Circular wait

A → B → A in a cycle. Break it: one global lock order, obeyed everywhere.

Deadlock.java
public class Deadlock {
    private final Object a = new Object();
    private final Object b = new Object();

    void aThenB() {                      // thread 1 takes a, then b
        synchronized (a) {
            synchronized (b) { work(); }
        }
    }

    void bThenA() {                      // thread 2 takes b, then a 💀
        synchronized (b) {
            synchronized (a) { work(); } // circular wait: both BLOCKED
        }
    }

    // FIX 1 — one lock order, everywhere, no exceptions
    // FIX 2 — bounded acquisition: never wait forever
    boolean tryAB() throws InterruptedException {
        ReentrantLock la = new ReentrantLock();
        ReentrantLock lb = new ReentrantLock();
        if (!la.tryLock(50, TimeUnit.MILLISECONDS)) return false;
        try {
            if (!lb.tryLock(50, TimeUnit.MILLISECONDS)) return false;
            try { return work(); }
            finally { lb.unlock(); }     // unlock in finally, always
        } finally { la.unlock(); }
    }

    void work() { /* ... */ }
}
🛑 Deadlock is invisible until it freezes production

It never throws, never logs, never times out — the process just stops making progress and CPU sits idle. Take jstack <pid> (or jcmd <pid> Thread.print) and look for a cycle of threads in BLOCKED, each waiting for a monitor another blocked thread owns. Fix it with a documented global lock order; use timeouts as the safety net, not the strategy.

Livelock is deadlock's restless cousin: both threads running, retrying and yielding, nothing progressing — two people sidestepping in a corridor. It comes from optimistic retry loops with no backoff. Starvation is a thread that never wins because greedy threads re-acquire continuously; a fair ReentrantLock(true) fixes it at a real cost to throughput, which is a trade-off to make consciously.

Cooperation: wait, interruption, ThreadLocal

Threads hand work to each other through the monitor's wait set: call wait() inside a synchronized block to release the lock and sleep, then be woken by notify() or notifyAll(). And you must — must — wrap that call in while, never if.

ProducerConsumer.java
final class Box {
    private int items = 0;
    private static final int FULL = 16;

    void produce() throws InterruptedException {
        synchronized (this) {
            while (items == FULL) wait();   // WHILE — never `if`
            items++;
            notifyAll();                    // wake everyone, they recheck
        }
    }

    void consume() throws InterruptedException {
        synchronized (this) {
            while (items == 0) wait();      // re-test after EVERY wakeup
            items--;
            notifyAll();
        }
    }
}
🚫 Myth: "if (cond) wait() is fine, I checked first"

Two reasons the while is mandatory. First, the JVM is permitted to deliver spurious wakeups — wait() can return with no notify at all. Second, with several consumers, another thread can take the item between your wakeup and your reacquisition of the monitor; an if proceeds on a condition that is no longer true. notifyAll() over notify() for the same reason: a single notify may wake a thread that can't use the item, leaving the one that can still asleep.

Interruption, join, and never swallowing the flag

Java has no thread kill — stop() is deprecated because it can release monitors halfway through an invariant. Control is cooperative: t.interrupt() sets a flag, and blocking methods (sleep, wait, join, BlockingQueue.take) notice by throwing InterruptedException. t.isInterrupted() reads the flag, Thread.interrupted() reads and clears it, and join() blocks until the thread reaches TERMINATED.

Shutdown.java
void shutdown(Thread worker) throws InterruptedException {
    worker.interrupt();                    // ask politely; do not kill
    worker.join(1_000);                    // wait up to 1s for TERMINATED
    if (worker.isAlive()) log.warn("worker ignored its interrupt");
}

void loop() {
    while (!Thread.currentThread().isInterrupted()) {
        process(queue.take());             // throws when interrupted
    }
}

// When you cannot propagate the exception, put the flag back:
catch (InterruptedException e) {
    Thread.currentThread().interrupt();     // restore it
    throw new IllegalStateException("shut down", e);  // or return
}

Swallowing InterruptedException is one of the most common concurrency sins: it silently destroys the caller's ability to shut you down, because an executor awaiting termination now believes your task ignored it. Either rethrow it, or restore the flag with Thread.currentThread().interrupt().

ThreadLocal<T> gives each thread its own value — the classic fix for non-thread-safe helpers like SimpleDateFormat, and how request context gets stashed without threading it through fifteen signatures. Its trap is the thread pool: threads live forever and are reused, so a set() with no matching remove() leaks that value for the pool's whole life and can leak yesterday's request context into today's request. Always remove it in a finally, and prefer Java 21's ScopedValue (preview) once you're on virtual threads, where thousands of threads would otherwise mean thousands of copies.

Chapter 15

Executors, CompletableFuture & virtual threads

A platform thread costs about 1 MB of stack and a kernel scheduling entity, so new Thread() per request dies at a few thousand connections — this chapter is about the three tools Java offers instead: bounded pools for real parallelism, CompletableFuture for composing concurrent work, and virtual threads for making ten thousand blocking tasks cheap.

Spawning a raw thread per task fails in three separate ways: creation and context switches are syscalls, 1 MB of stack per thread turns 10 000 connections into 10 GB of resident memory, and the OS scheduler degrades long before that. The fix since Java 5 has been to separate the task from the thread — you submit work, an ExecutorService decides which thread runs it and how many exist.

The second problem is compositional: two Futures cannot be joined without blocking a thread, so expressing "fetch A and B, then combine" means hand-built latches. CompletableFuture fixes that with a chainable, non-blocking graph. And Java 21's virtual threads attack the first problem from below — thousands of threads that cost kilobytes each, because the JVM, not the OS, schedules them.

⚠️ Why everyone stopped using the Executors factories

newFixedThreadPool hands you a LinkedBlockingQueue with no capacity: producers outpace consumers and the queue grows until the heap dies — with the pool looking perfectly healthy. newCachedThreadPool makes the opposite mistake: an unbounded thread count, so a burst of slow requests creates tens of thousands of OS threads and the machine starts swapping.

Pools.java
ExecutorService pool = new ThreadPoolExecutor(
    8,                                  // core
    16,                                 // max — hard ceiling
    60, TimeUnit.SECONDS,               // idle threads reaped
    new ArrayBlockingQueue<>(1000),     // BOUNDED: back-pressure
    r -> {                              // named, daemonised threads
        Thread t = new Thread(r, "worker");
        t.setDaemon(true);
        return t;
    },
    new ThreadPoolExecutor.CallerRunsPolicy()); // reject = slow the caller

pool.execute(() -> work());            // void: failures hit the handler
Future<Integer> f = pool.submit(() -> compute());  // Future + exceptions
pool.shutdown();                       // stop accepting…

execute takes a Runnable and returns nothing — if it throws, the exception dies in the thread's uncaught-handler. submit wraps your work in a Future: return values arrive through get(), and exceptions come back wrapped in ExecutionException. CallerRunsPolicy is the elegant part of that example: when the queue is full, the submitting thread runs the task itself, which is back-pressure that throttles the producer for free.

Future — the API that can't compose

Future is deliberately minimal, and the pain shows the moment work must happen together:

CompletableFuture<String> page(String url) {
    return CompletableFuture.supplyAsync(
        () -> httpClient.body(url), POOL);      // never the common pool
}

Page loadAll() {
    CompletableFuture<String> a = page("https://a.example");
    CompletableFuture<String> b = page("https://b.example");
    CompletableFuture<String> c = page("https://c.example");

    // zip two independent futures — no thread waits for the other
    CompletableFuture<Page> header =
        a.thenCombine(b, (x, y) -> new Page("head", x + y));

    // fan out the rest, then join — still zero blocked threads
    CompletableFuture.allOf(header, c).join();
    return new Page("home", header.join().body() + c.join());
}
🧠 Callbacks run on the completing thread

A bare thenApply executes on whichever thread finished the previous stage — often a pool thread you don't own. If your callback blocks (a JDBC query, a big JSON parse), you stall someone else's worker. Pass an executor: thenApplyAsync(fn, POOL). Rule of thumb: keep callbacks non-blocking, and hand anything blocking to an explicit executor — or to a virtual thread.

thenApply vs thenCompose — map vs flatMap

The single most common CompletableFuture mistake is using thenApply on a function that already returns a future, which nests one future inside another (CompletableFuture<CompletableFuture<User>>) and needs a second join() to unwrap it. If the function returns a future, flatten it with thenCompose.

Chain.java
// ThenApplyWrapper is the bug: nested futures
CompletableFuture<Profile> nested =
    fetchUser(id)
        .thenApply(u -> fetchProfile(u.id()))   // CF<CF<Profile>> ❌
        .join().join();

// Flat: one level, one join — this is what you meant
CompletableFuture<Profile> flat =
    fetchUser(id)
        .thenCompose(u -> fetchProfile(u.id())) // CF<Profile> ✅
        .exceptionally(ex -> Profile.anonymous()) // recovery
        .whenComplete((p, ex) -> log(p, ex));     // side effect, passes on

// thenApply   = map     (function returns a plain value)
// thenCompose = flatMap (function returns a future)
// thenCombine = zip     (two independent futures, one function)

Three more you'll want: exceptionally recovers from failure with a fallback; whenComplete observes the result (or the exception) and passes it through untouched — good for logging, useless for recovery; handle takes both value and exception, letting you normalise success and failure in one branch. anyOf completes when the first branch does — the shape of every timeout or redundant-fallback pattern.

Virtual threads — Project Loom, Java 21

A virtual thread is a thread the JVM schedules onto a small pool of carrier platform threads — an M:N scheduler, the same idea as Go's goroutines or Kotlin's coroutines. When a virtual thread blocks on I/O, the JVM parks it, moves the carrier to another virtual thread, and resumes it later. One carrier is now a multiplexed lane, not a busy worker, so the economics flip: threads cost kilobytes, and creating one is a heap allocation rather than an OS call.

VirtualThreads.java
// (1) plain as a Thread — but it costs kilobytes, not 1 MB
Thread vt = Thread.ofVirtual().name("vt", counter)
                  .start(() -> handleRequest());
vt.join();

// (2) the idiomatic form: one virtual thread per task, no queue at all
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> results = urls.stream()
        .map(u -> executor.submit(() -> httpClient.body(u)))
        .toList();
    for (Future<String> f : results) System.out.println(f.get());
}

// 50 000 concurrent HTTP calls, ~50 000 virtual threads,
// a handful of carriers (default = number of CPU cores).

What they're for: thousands of tasks that spend their lives waiting — HTTP calls, JDBC queries, file reads, sleeps. What they are not: extra CPU cores. Eight cores still do eight computations at once, and a virtual thread stuck in a hot arithmetic loop only adds scheduling overhead. Virtual threads buy concurrency, never parallelism — Chapter 14's locks still apply, because they are still real threads with a real Java Memory Model.

🛑 Pinning: the one virtual-thread trap on Java 21

A virtual thread that blocks inside a synchronized block can get pinned — it holds its carrier hostage, and every other virtual thread waiting for that carrier stalls behind it. On Java 21–23 this is real; diagnose it with -Djdk.tracePinnedThreads=full. Java 24 (JEP 491) reworked monitor entry so synchronized no longer pins in these cases, so the safe rule is: on 21, keep blocking I/O out of synchronized (or use ReentrantLock); on 24+, it mostly stops mattering. Native (JNI) calls can still pin on any version.

Structured concurrency — preview in Java 21 as StructuredTaskScope — applies the same discipline to a fan-out: subtasks are scoped, so the scope cannot finish until every child has either succeeded or been cancelled, and a failure cancels the siblings instead of leaking. It's try-with-resources for parallel work, and it's the API that makes virtual threads safe to use at scale.

🚫 Myth: "async makes Java faster"

The Kotlin counterpart: coroutines

Kotlin's answer to this whole chapter is kotlinx.coroutines, and it's a better default: suspend functions, structured concurrency built into every scope, and Dispatchers.IO — a pool sized for exactly the "thousands of blocking tasks" case. async/await mirrors CompletableFuture/join with less ceremony, and awaitAll is allOf.

Fetch.kt
suspend fun loadAll(urls: List<String>): String =
    coroutineScope {                       // structured: waits for children
        val deferred = urls.map { url ->
            async(Dispatchers.IO) {        // IO pool — made for blocking
                httpClient.body(url)
            }
        }
        deferred.awaitAll().joinToString("")   // allOf(...).join()
    }

suspend fun profile(id: Long): Profile =
    runCatching { fetchProfile(fetchUser(id).id) }
        .getOrElse { Profile.anonymous }       // exceptionally

// Failure in any child cancels the scope — you get that for free.

Note the shape difference: Java's CompletableFuture is an explicit object graph you thread through your code, while Kotlin's coroutines are language-level — suspend reads like ordinary sequential code, and the compiler transforms it into a state machine instead of blocking a thread. Under the hood both solve the identical problem: stop dedicating a thread to waiting.

✅ What to remember
  • Never take an unbounded queue or unbounded thread count — build ThreadPoolExecutor with a bounded queue and a rejection policy.
  • execute = fire and forget; submit = returns a Future and wraps failures in ExecutionException.
  • Future blocks and can't compose — that's the whole reason CompletableFuture exists.
  • thenCompose when the function returns a future; thenApply when it doesn't.
  • Pass an executor to *Async — bare callbacks run on the completing thread, which isn't yours.
  • Virtual threads = concurrency, not parallelism: perfect for blocking I/O, pointless for maths.
  • Keep blocking I/O out of synchronized on Java 21–23; Java 24 (JEP 491) largely removed the pinning.
  • Default to blocking code + virtual threads; add CompletableFuture only to compose concurrent branches.
Chapter 16

Inside the JVM: bytecode, memory & GC

The JVM is the reason your code is portable — and the reason a for-loop can finish faster than you wrote it. This chapter opens it up: what a .class file actually contains, how classes get loaded, where objects live at runtime, which collector reclaims them, and how the JIT turns your bytecode into machine code (and occasionally throws it away again).

You have been shipping .class files since Chapter 01 without looking inside one. That's fine until something odd happens: a class loads twice, a static initialiser runs at an unexpected moment, a "tiny" allocation eats the heap, or your loop is mysteriously slow on the first request. All four are explained by what's in this chapter, and none of it is exotic — it's the machinery every Java process runs on.

Bytecode is a stack machine: there are no registers to address, just an operand stack that instructions push onto and pop from. Watch a two-line class disassemble:

Class loading — seven phases, three loaders

Loading happens lazily: a class is opened when it's first needed, not at startup. Then five more phases run — linking is the umbrella for the middle three:

1 · loading Find the bytes (classpath, JAR, module) and produce a Class object for them.
→
2 · verify Structural check: types line up, the stack depth is right, no jump lands mid-instruction. Corrupt or hostile bytecode dies here.
→
3 · prepare Allocate static fields and set them to their defaults (0, null, false). No user code runs yet.
→
4 · resolve Turn symbolic constant-pool references into direct ones — the lazy step, usually done on first use.
→
5 · initialize Run <clinit>: static blocks and static field assignments, exactly once, thread-safe. Now the class is ready.

Those last two phases explain classic surprises: a static field is null before initialisation runs (preparation), and a class's static block executes at the moment something first touches the class — not when the program starts.

bootstrap Loads the JDK core: java.lang, java.util, everything in java.base. Implemented in native code and associated with null as its loader.
→
platform Java 9+'s middle layer: module-aware loaders for the non-core platform modules (java.sql, jdk.unsupported…).
→
application Your classpath. Also handed out as Thread.currentThread().getContextClassLoader() — what frameworks use to find your classes.
🧠 Why delegation asks the parent first

The application loader doesn't try your classpath first — it asks the platform loader, which asks the bootstrap loader, and only falls back on the way down. So java.lang.String always comes from the JDK: dropping a forged java/lang/String.class on the classpath is ignored rather than loaded, which is the JVM's original class-spoofing defence. It also keeps one runtime definition per class name. The escape hatch when you need parent-last behaviour (JDBC drivers, SLF4J bindings) is the thread context class loader.

Key insight: a method's locals are free and precise — the JVM knows exactly where every reference is, so it can trace them as GC roots. An Object on the heap costs an allocation, a header and a garbage-collector visit later.

Object layout is where the cost hides. Every object starts with a header: an 8-byte mark word (hash code, lock bits, GC age) plus a class pointer — compressed to 4 bytes on heaps under 32 GB. Fields follow in declaration order, padded to an 8-byte boundary. That's why Integer in an array is expensive:

Layout.java
int[] primitives = new int[1_000_000];     // ~4 MB, contiguous, SIMD-friendly
Integer[] boxed   = new Integer[1_000_000]; // 4 MB of REFERENCES + 1M objects
for (int i = 0; i < boxed.length; i++) {
    boxed[i] = primitives[i];   // 1,000,000 allocations, 16 B each ≈ 16 MB
}                               // plus one pointer chase per element

// The JIT can make allocations disappear — if they never escape:
static long hotLoop(int n) {
    long acc = 0;
    for (int i = 0; i < n; i++) {
        Point p = new Point(i, i + 1);  // never leaves this method
        acc += p.x();                   // → scalar-replaced: NO allocation
    }
    return acc;
}
// Watch it happen: -XX:+UnlockDiagnosticVMOptions -XX:+PrintEscapeAnalysis

The second half is escape analysis: if the JIT proves an object never escapes the method, it keeps the fields in registers and never allocates it at all — scalar replacement. That's why new Object() in a hot loop can cost nothing, and why an innocent-looking refactor that lets an object escape (return it, store it in a field) can triple your allocation rate overnight.

Garbage collection

The collector never "scans the heap looking for garbage" — it starts from the roots and marks everything reachable: local variables on every thread's stack, static fields, JNI references, and a few runtime internals. Anything unmarked after the trace is unreachable and gets reclaimed, at some point, when the collector runs. Reachability is the only definition of liveness; an object with a non-null reference that no root can reach is still garbage, and an object nobody can reach but that's still linked from a root is very much alive.

Because roughly 98% of objects die before their first birthday, the heap is split: new objects land in Eden, survivors of a young-collection copy between two Survivor spaces while ageing, and anything that survives long enough is promoted to the old generation. That's the generational hypothesis, and it's why minor collections are cheap — most of Eden is already dead, so there's almost nothing to copy.

🚫 Myth: "Tune the GC first"

Most production Java services need exactly one memory decision — a sensible -Xmx, ideally with -Xms set to match so the heap never resizes under load — and then nothing else. G1 is the default and is rarely the bottleneck people assume it is.

The order that works: set the heap size → measure with -Xlog:gc* and JFR → identify the actual problem → change one flag → measure again. Choose ZGC because your pause SLO is violated and your logs prove it, not because a blog called it "sub-millisecond". Fix your allocation rate and your leak first; they are almost always the real bug.

⚠️ The two heap failures worth recognising

Heap too small: the collector runs constantly, spends most of its time in old-gen collections and finally throws OutOfMemoryError: Java heap space — the log shows full GCs reclaiming almost nothing, which means a live-set problem, not a sizing one. Metaspace leak: too many class loaders (typically frameworks loaded in a hot-redeploy loop) exhaust native memory and throw OutOfMemoryError: Metaspace; cap it with -XX:MaxMetaspaceSize=256m so it fails loudly instead of quietly eating the host.

The JIT: interpreter → C1 → C2

HotSpot doesn't compile on startup — it watches. Code begins in the interpreter, and once a method (or a loop, via on-stack replacement — OSR lets a method already executing swap into compiled code mid-loop) accumulates enough invocations, a fast compiler (C1) compiles it while collecting profiles: which branches are taken, which types actually appear, which null checks never fail. When a method proves really hot, C2 recompiles it using those profiles — inlining aggressively, unrolling loops, eliminating the null checks it has evidence for, and vectorising. Roughly: interpreter counts, C1 compiles fast, C2 compiles well.

Two consequences you must design for. First, warm-up: the first seconds of a JVM run are interpreter- and C1-speed, and steady state can be 10–100× faster, which is why a server's early latency numbers lie. Second, the JIT optimises with evidence, and evidence can be invalidated — hence deoptimisation: compiled code is discarded, execution falls back to the interpreter, and later gets recompiled. It's normal, but a spike right after a new class loads or an uncommon branch fires is almost always this.

🧠 Never benchmark Java with a stopwatch

A hand-rolled loop measures three things that aren't your code: interpreter warm-up, tier transitions, and the JIT's ability to delete the entire benchmark because nothing observable happens to the result. Use JMH — it forks a fresh JVM, warms up properly, consumes values through a Blackhole so dead-code elimination can't cheat, and reports confidence intervals.

build.gradle
plugins {
    id 'me.champeau.jmh' version '0.7.2'
}

jmh {
    benchmarkMode = ['avgt']     // average time per operation
    timeUnit     = 'us'
    fork         = 2             // fresh JVM per run — honest isolation
    warmupIterations = 5         // let the JIT reach C2 first
    iterations   = 5
}

// ./gradlew jmh  — never System.currentTimeMillis() in a for-loop.

✅ What to remember
  • A .class file starts with 0xCAFEBABE, then version, constant pool, then fields, methods and attributes.
  • javap -c reads bytecode: aload_0 = this, getfield/putfield = fields, invokevirtual = dispatch, ireturn/areturn = results.
  • Loading → verify → prepare → resolve → initialize; a class initialises on first use, not at startup.
  • Loaders delegate parent-first — that's why your java.lang.String can never replace the JDK's.
  • Stack = frames and primitives, private and free. Heap = shared objects, Eden → Survivor → old gen. Metaspace and the code cache live off-heap.
  • GC marks from roots (stack locals, statics, JNI) — reachability, not null-ness, decides liveness.
  • G1 is the default and usually correct; measure with -Xlog:gc* before touching a tuning flag.
  • Escape analysis can delete allocations — and any microbenchmark you didn't write with JMH.
  • Kotlin emits the same bytecode plus kotlin.Metadata and real null checks — this whole chapter is your chapter too.

Performance & how Java compares

Java is fast in the way a motorway is fast: not the quickest single lap, but predictable throughput at scale, forever, without a developer stopping to refuel.

The honest framing first. Java will not beat C or Rust on a tight numeric loop, because those languages hand you the CPU with nothing in between. What Java offers instead is a JIT compiler that optimises based on what your program actually does, a collector that removes an entire category of bugs, and identical behaviour on every platform you deploy to.

The warm-up story

Every Java benchmark that ignores warm-up is lying to you. The JVM starts by interpreting, measures which methods are hot, compiles them with C1, then recompiles the very hottest with full profile-guided optimisation. Throughput climbs, then plateaus.

→

You'll measure the interpreter, not the language. Use JMH, which handles warm-up, dead-code elimination and blackhole consumption for you. If your numbers came from a stopwatch, they're an anecdote.

🚫 Myth: "Kotlin is slower than Java"

What actually makes Java code slow

🧵

Blocking on one lock

Threads parked behind a single synchronized block serialise your whole service. Measure lock contention before optimising anything else.

垃圾

Allocation storms

Creating millions of short-lived objects per second gives the GC constant work. It's survivable — but it's measurable churn. Prefer reuse for hot paths.

📦

Unbounded queues

Memory grows until the process dies. A queue must have a bound and a rejection strategy, or it isn't a queue — it's a slow leak.

⏱️

Chatty I/O

One round trip per record in a loop. Batching to a database is routinely a 100× win — far larger than any language-level micro-optimisation.

💡 The performance order of operations
  • Measure first. JMH for code, a profiler for services, a flame graph for truth.
  • Fix the algorithm. O(n²) → O(n log n) beats any JIT trick available.
  • Fix the I/O pattern. Batch, cache, and pipeline before touching arithmetic.
  • Then look at allocation and locks — usually together.
  • Never hand-optimise readability for an unmeasured guess.
🧠 Where Java genuinely loses

Cold start and memory floor. A minimal JVM wants tens of megabytes and hundreds of milliseconds before your main runs — a poor fit for CLI tools and short-lived serverless functions. This is why Project CRaC (checkpoint/restore), Project Loom and the GraalVM native image path exist. For a server that lives for hours, none of it matters.

Kotlin is a statically-typed language from JetBrains that compiles to JVM bytecode — designed specifically to remove Java's sharpest edges without leaving the runtime you already run in production.

JetBrains builds IntelliJ IDEA, the IDE most Java developers use. Writing a Java IDE means staring at Java's pain points eight hours a day, for years. Kotlin is what happened when the people best positioned to fix those problems decided to write a new language instead of filing more bug reports.

Kotlin basics: variables, types & functions

Kotlin has two kinds of variable, almost no boilerplate, and functions that can return values directly from an expression — the syntax habits that make the rest of Part II feel fast.

Coming from Java, the first thing you notice is that almost everything is shorter. The second thing you notice is that the compiler refuses more of what you write. Both are deliberate.

val and var

Every variable declares up front whether it can be reassigned. There is no final keyword — it's part of the declaration.

Basics.kt
fun main() {
    val score = 10          // read-only binding — cannot be reassigned
    var count  = 0          // mutable
    count += 1

    // score = 20           // ❌ compile error: val cannot be reassigned

    println("$score, $count")   // 10, 1
    println("sum = ${score + count}")  // ${} for expressions
}
✅ Use val when…
  • It's a constant or the value never changes
  • You want to prove a value is stable
  • Ninety percent of declarations — this is the default
✅ Use var when…
  • You're accumulating into a counter or buffer
  • The value genuinely mutates during a scope
  • A loop variable that changes each iteration
🧠 val ≠ immutable object

val means the binding can't change, not the value. val list = mutableListOf(1) then list.add(2) is perfectly legal. Immutability of contents needs an immutable type — listOf(1). Java's final has exactly the same trap.

Null safety: the billion-dollar fix

Java's null is the value that can appear anywhere, satisfies no type contract, and crashes billions of dollars of software a year. Kotlin moves it into the type system — String and String? are different types.

Java can't tell the difference between a variable that holds a string and one that might hold null. Kotlin can, because it requires you to say: ? marks a type as nullable, and the compiler then enforces every path.

❌ Java — compiles, crashes later 
String name = user.getName();
int len = name.length();   // compiles fine
                         // NPE at 3am if getName() returned null

// Java 8+ workaround
String safe = Optional.ofNullable(user.getName()).orElse("anon");

Nothing in the signature tells you nullability. Every call is a bet.

✅ Kotlin — refuses to compile 
var name: String = user.name
name.length                 // ✅ String is never null — safe by construction

var maybe: String? = user.email
maybe.length                // ❌ compile error: only safe calls allowed
maybe?.length               // ✅ Int? — result may be null, type says so

The type system rejects the bug before it exists. Nullability is in the API.

The four operators

NullOps.kt
fun describe(user: User?): String {

    // 1. Safe call — ?.  returns null if the receiver is null
    val city: String? = user?.address?.city
    // chains freely; the whole chain is null if ANY link is null

    // 2. Elvis — ?:  give a default when the left side is null
    val name: String = user?.name ?: "anonymous"

    // 3. Not-null assertion — !!  "I guarantee this is non-null"
    val forced: String = user!!.name   // throws NPE if user is null

    // 4. Smart cast — compiler narrows after a null check
    if (user != null) {
        return user.name               // no !!, no ?., no cast
    }
    return "anonymous"
}

    val shown: String = u?.address?.city ?: "unknown"
    println(shown)           // unknown when u or address is null

    u?.let {
        println("hello ${it.name}")
    }

    val greeting = u?.name?.let { "hi $it" } ?: "who?"

    // ?: with a lazy default — don't build the expensive value unless needed
    val config = loadConfig() ?: defaultConfig()

    // Chain Elvis operators for layered fallbacks
    val theme = prefs.theme ?: env.theme ?: "dark"
}
⚠️ !! is a deferred crash

user!!.name is exactly the Java NullPointerException you came to Kotlin to escape — just with a different syntax. It's occasionally justified at a boundary where you've already proven non-null, but a codebase full of !! is a Java codebase with better formatting. Search for !! before merging any Kotlin PR.

🚫 Myth: "Kotlin still throws NPEs"

True, but far less often. The real sources are: platform types from Java (String! — see below), !!, lateinit before assignment, and unboxing a null in an unexpected place. Eliminate the first two and NPEs stop being a normal part of your logs.

Platform types: the seam with Java

When Kotlin reads a Java declaration it can't know if it returns null. So it uses a platform type, written String! — "unknown, could be either". Kotlin lets you treat it as non-null or nullable.

platform.kt
// Java: public String getName() { return maybeNull; }

val a: String  = javaObj.name   // compiles — you promised it's non-null
val b: String? = javaObj.name   // compiles — you're being cautious
val c = javaObj.name            // platform type String!

// Rule of thumb:
//   Java API you don't control  → treat as String? (defensive)
//   Java API you've verified    → String is fine
//   Your own Kotlin called from Java → declare ? or non-null explicitly
🧠 Annotating Java so Kotlin knows

Add JetBrains' @Nullable/@NotNull (or JSR-305, or javax.annotation) to your Java APIs. The moment you do, Kotlin's compiler enforces null-safety across the boundary. This is how a Java/Kotlin codebase gets gradually safer rather than staying as weak as its Java half.

Kotlin classes, data & sealed types

Kotlin's classes are final by default, constructors live in the header, and everything you'd write by hand in Java — equals, copy, destructuring — comes from one modifier.

The Java chapters covered classes, inheritance and data modelling separately. Kotlin folds most of it together: a primary constructor, property declarations in the header, data for value semantics, and sealed for closed type hierarchies.

Person.kt
// Primary constructor lives in the class header
class Person(val name: String, val age: Int) {

    // Property with a custom getter — computed, not stored
    val isAdult: Boolean
        get() = age >= 18

    // Secondary constructor must delegate to the primary
    constructor(name: String) : this(name, 0)

    // init blocks run in declaration order alongside property initializers
    init {
        require(age >= 0) { "age must not be negative: $age" }
    }

    // Member function
    fun greet() = println("Hi, I'm $name")
}

fun main() {
    val p = Person("Ada", 36)
    println(p.name)      // property, not getName()
    println(p.isAdult)   // getter runs each access
    p.greet()
    println(p)           // Person(name=Ada, age=36) — toString is generated
}
✅ Classes are final by default

Kotlin inverts Java. You must write open class to allow inheritance — so every new hierarchy is a deliberate decision. This is Effective Java's "design for inheritance or forbid it", enforced by the language.

✅ val in the header = read-only property

class P(val name: String) generates a private field, a getter, and a constructor parameter — one word doing what Java spreads across four lines. Use var only when mutation is intended.

⚠️ val is not a deep immutable

class Box(val items: MutableList<String>) can't have its items field reassigned, but the list itself is fully mutable. Same rule as Java's final from chapter 03: the binding is fixed, the contents may not be. Use listOf and Map for real immutability.

Sealed hierarchies

Result.kt
// Sealed: every subtype is known at compile time (same package/module, Kotlin 1.5+)
sealed interface Result<out T>
data class Ok<T>(val value: T) : Result<T>
data class Err(val message: String, val cause: Throwable?) : Result<Nothing>

fun <T> compute(x: T): Result<T> = when {
    x == null -> Err("null input", null)
    else      -> Ok(x)
}

// Exhaustive when — add a subtype and THIS becomes a compile error
fun describe(r: Result<*>): String = when (r) {
    is Ok   -> "ok: ${r.value}"
    is Err  -> "failed: ${r.message}"
    // no else needed — the compiler proved it's exhaustive
}

// when as an expression, with smart casts inside
val (label, detail) = when (val r = compute(41)) {
    is Ok  -> "success" to r.value.toString()
    is Err -> "error" to r.message
}

🧠 Sealed vs enum

Kotlin's collection API is small, coherent and reads left to right — and its functions take a trailing lambda so pipelines look like sentences rather than nested calls.

The same interfaces you know — List, Set, Map — but with immutable factories as the default and extension functions doing the work that required Collectors in Java.

Creating.kt
// Immutable by default — these are the ones to reach for

Two habits make Kotlin collections read well. "a" to 1 builds a Pair — that's how map literals work. And because a lambda is always the last parameter, you can move it outside the parentheses: list.filter { … } instead of list.filter({ … }). 🧠 Contracts: telling the compiler

    return requireNotNull(value)

Coroutines: concurrency without threads

A coroutine is a function you can suspend and resume. Thousands can be in flight while a handful of threads serve them — which is why Kotlin treats concurrency as a language feature rather than an API.

Java's answer to this problem arrived as virtual threads (Project Loom, chapter 15). Kotlin's arrived a decade earlier, in the language itself: suspend marks a function that can pause, and the compiler rewrites its body into a state machine.

⏸️

suspend

The function may suspend without blocking. It can only be called from a coroutine — the compiler enforces this.

🏗️

Builder

launch, async, runBlocking create a CoroutineScope and start work.

🧵

Dispatcher

Decides which thread resumes the coroutine: Default, IO, Dispatchers.Main.

Hello.kt
import kotlinx.coroutines.*

suspend fun fetchUser(id: String): User {
    delay(200)                       // suspends, does NOT block the thread
    return User(id, "Ada")
}

fun main() = runBlocking {           // bridges sync world → coroutine world
    println("before")

    val job = launch {               // fire and forget — returns Job
        val u = fetchUser("u1")
        println("got ${u.name}")
    }

    val deferred: Deferred<String> = async {   // returns a value
        fetchUser("u2").name
    }

    job.join()                       // wait for that one
    println("name=${deferred.await()}")        // get that one
    println("after")
}
❌ Java-style: threads block

Threads cost ~1 MB of stack each and are expensive to schedule. Thread-per-request caps you in the low thousands.

✅ Kotlin: coroutines suspend

    db.write(u)                      // resumes later, maybe on another thread

The thread is released the moment the coroutine waits. Concurrency becomes a count of logical tasks, not OS threads.

🧠 What suspend actually compiles to

The compiler transforms the function body into a state machine: each suspension point is a label, and the Continuation object carries local variables across the pause. Nothing magical runs on another thread by itself — that's the dispatcher's job. It also means a coroutine's locals live in a heap object, not on a stack frame, which is exactly how virtual threads do it too.

Structured concurrency: scopes

Every coroutine belongs to a scope. When the scope ends, its children are cancelled. This single rule is what stops leaks and orphaned work — the failure mode of raw thread management.

Scopes.kt

🧠 Cancellation is cooperative

        } catch (e: Exception) {

        }

suspend fun riskyLoop() {

There's still a thread under every resumed coroutine — the dispatcher decides which one. Blocking a dispatcher thread with Thread.sleep or JDBC is still a bug: it stalls every coroutine scheduled behind you.

Flow: reactive streams on coroutines

A Flow is a cold, suspending sequence of values — Java's Stream crossed with Publisher, but with none of the ceremony and backpressure handled by default.

Two shapes cover almost everything: Flow for an ordered sequence of values, and StateFlow/SharedFlow for a current value that new subscribers can observe. Both are built on coroutines, so every rule from chapter 25 applies.

❄️

Cold

Nothing runs until collected, and each collector gets its own fresh run. A flow isn't "something happening" — it's a recipe.

⏸️

Backpressured

Collection pace drives production. A slow collector slows the producer instead of overflowing a buffer.

🧯

Structured

Cancelling the collecting coroutine cancels the producer. No orphaned subscriptions.

Basics.kt
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

// Building a flow — suspending, one value at a time
fun numbers(): Flow<Int> = flow {
    for (i in 1..5) {
        delay(100)                  // suspends — not blocking
        emit(i)                     // hand a value to the collector
    }
}

suspend fun main() = runBlocking {
    // Nothing happens until collect
    numbers().collect { value -> print("$value ") }   // 1 2 3 4 5

    // Transform operators — same shape as sequences
    numbers()
        .filter { it % 2 == 1 }
        .map { it * it }
        .take(2)
        .collect { println(it) }     // 1, 9

    // Terminal with a result
    val sum = numbers().reduce { a, b -> a + b }
    val first = numbers().first()
    val list  = numbers().toList()
}
⚠️ emit only inside its own flow { }

Calling emit from a nested lambda or another coroutine throws IllegalStateException. flow { } gives you a scope tied to the collector — that's what makes backpressure and cancellation work. For multiple sources, use channelFlow.

Operators.kt
data class Tick(val seq: Long, val price: Double)

    // Intermediate — lazy, runs per value
    ticks()
        .filter { it.price > 100.0 }
        .distinctUntilChanged()          // suppress repeats — essential for signals
        .debounce(250)                   // wait for a pause in a bursty stream
        .onEach { audit.log(it) }        // side effect without changing values
        .collect { println(it) }

    // Combining and flattening
    val a: Flow<Int> = flowOf(1, 2, 3)
    val b: Flow<String> = flowOf("x", "y")

    a.zip(b) { n, s -> "$n$s" }.collect { print("$it ") }   // 1x 2y
    a.combine(b) { n, s -> "$n$s" }                          // emits on either

    // Merging concurrent sources
    merge(flowOf(1, 3), flowOf(2, 4)).collect { print(it) }  // interleaved

    // Flattening a flow of flows — flatMapConcat vs Latest vs Merge
    a.flatMapConcat { n -> flowOf(n, n) }.toList()   // sequential, in order
    a.flatMapLatest { n -> flowOf(n) }.toList()      // newest wins, old cancelled
}

StateFlow & SharedFlow

class SearchViewModel : CoroutineScope {

    private val _query = MutableStateFlow("")          // write side
    val query: StateFlow<String> = _query.asStateFlow() // read-only exposure

    // SharedFlow: multi-subscriber events, no replay by default
    private val _events = MutableSharedFlow<UiEvent>()
    val events: SharedFlow<UiEvent> = _events.asSharedFlow()

    val results: StateFlow<List<Item>> = _query
        .debounce(300)
        .distinctUntilChanged()
        .flatMapLatest { q ->
            if (q.isBlank()) flowOf(emptyList()) else search(q)
        }
        .stateIn(
            scope = this,
            started = SharingStarted.WhileSubscribed(5_000),  // stop 5s after last UI
            initialValue = emptyList()
        )

    fun onQueryChanged(s: String) { _query.value = s }
}
✅ StateFlow

A current value with history of exactly one. Always has something to give a new collector, conflates rapid updates, and never emits duplicates. Use for UI state: one screen, one truth.

✅ SharedFlow

A stream of events — navigation, toasts, one-shot effects. Configurable replay and buffer. Each subscriber sees what it subscribed to, so an event never happens twice or zero times by accident.

🚫 Myth: "Flows are Rx with worse syntax"

The concepts map closely — Flow ≈ Observable, operators correspond one for one. But Flow is much smaller by design: no Observable/Observer/Scheduler triple, no observeOn, no custom backpressure protocol. Cancellation comes free from coroutines, and the cold/hot distinction is one sentence rather than an operator taxonomy.

⚠️ StateIn, not collect-in-a-launch

Starting launch { flow.collect { … } } to feed a field is a leak waiting to happen — it outlives the UI and ignores lifecycle. stateIn/shareIn bind the collection to a scope with an explicit SharingStarted policy. For Compose, just call collectAsStateWithLifecycle().

✅ Scoring honestly

Part 1 — Java fundamentals

1. Why does int[] a = {1,2,3}; int[] b = a; b[0] = 9; change a, while the equivalent with int x = 1 doesn't?

Primitives hold their value directly, so assignment copies the value. An array variable holds a reference to a heap object — assignment copies that address, and both names then point at the same object. This is why chapter 03's rule is "primitives copy, references copy the address".

2. What's wrong with using double for a bank balance?

Binary floating point can't represent most decimal fractions exactly (0.1 + 0.2 == 0.3 is false). Errors accumulate over arithmetic and rounding. Use BigDecimal with an explicit scale, or store integer cents in a long.

3. When is a record the wrong choice for a domain type?

When identity matters more than content. Records have value equality, so two instances with identical components are interchangeable — correct for Money, wrong for an Order identified by its database ID. Mutable entities (JPA-managed, var state) also break the immutability assumption.

4. What does instanceof String s give you over plain instanceof?

A binding: s is declared and narrowed to String inside the block, eliminating the separate cast and the mismatched-cast class of bug. Combined with && guards (instanceof String s && s.length() > 3) and switch patterns with when, it replaces the old cast-then-check dance entirely.

5. Why must desc be declared before a classic switch that assigns it?

Because a switch with fall-through can't guarantee a branch assigns it — the compiler's definite-assignment analysis fails, so desc "might not have been initialized". Switch expressions with -> fix this by requiring exhaustiveness: every path yields a value.

Part 2 — Java in practice

6. You're checking membership of IDs in a list, 100k times. Why is it slow and what's the fix?

List.contains is O(n) — 100k scans over a large list is O(n·m). Build a HashSet of the IDs first; contains is then O(1) and the cost becomes a single pass. Rule of thumb: if you call contains more than once, you wanted a set.

7. Why does calling list.remove(x) inside a for-each loop throw?

The iterator tracks a modification count and fails fast on structural change (ConcurrentModificationException) — a deliberate guard against silently skipping elements, even single-threaded. Use removeIf, an explicit Iterator.remove, or build a new list.

8. What's the difference between orElse and orElseGet?

orElse(T) evaluates its argument eagerly — it's built even when the Optional is present. orElseGet(Supplier) runs only when absent. Use orElseGet for anything with cost (a database hit, an object allocation), and orElseThrow when absence is genuinely exceptional.

9. Why should a Pattern be a static field?

Compilation is the expensive part — parsing and optimising the regex. Creating a new Pattern per call inside a loop repeats that cost for every input. Compile once, reuse the Pattern, create a fresh Matcher per input (Matchers aren't thread-safe; Patterns are).

10. Name two reasons a Java program is slow that no amount of code-level tuning will fix.

The classic pair: chatty I/O (one round trip per record — batching is routinely 100×) and lock contention (threads serialised behind one monitor). Also unbounded queues (memory growth until OOM) and an algorithmic choice like O(n²) where O(n log n) exists. All four are design problems, not syntax problems.

11. What does try-with-resources guarantee that finally often doesn't?

That every resource closes, in reverse declaration order, on every exit path — including when the body throws, and including the case where the first resource's constructor throws and later ones were already opened. Manual finally blocks routinely miss one path; suppressed exceptions tell you about failures during close.

12. What is a functional interface and why does it matter to lambdas?

An interface with exactly one abstract method — the target type the compiler uses to type-check a lambda. Runnable, Comparator, Function<T,R>; your own with @FunctionalInterface to catch accidental extra methods. It's why stream.map(u -> u.name()) compiles without an explicit cast.

Part 3 — Kotlin

13. What's the difference between val x: String? being null and x being an unassigned variable?

They're different states. A declared-but-unassigned local is a definite-assignment error the compiler rejects at use; a nullable String? is assigned, and its value may be null — so every access must be safe (?.), defaulted (?:) or proven non-null. Type nullability and initialisation are independent checks.

14. What does !! do that ? doesn't, and why avoid it?

!! asserts non-nullness: it returns the value as a non-null type, or throws an NPE if it was null — reintroducing the exact runtime failure Kotlin exists to prevent. It's legitimate only where you've already established non-nullness in a way the compiler can't see. A PR full of !! is a Java codebase with different punctuation.

15. data class generates six things. Which of these does it not generate?

It generates equals, hashCode, toString, copy, componentN functions, and the canonical constructor. It does not generate: validation, immutability of nested mutable objects, a no-arg constructor (needed by some serializers), or inclusion of superclass state in equality.

16. Why is a when over a sealed hierarchy better than one over an enum?

Both give exhaustiveness, but sealed variants are types with their own data — each branch can smart-cast and read its own fields (is Ok -> r.value), whereas enum constants are uniform instances. Sealed is for Success/Error/Loading; enums are for RED/GREEN/BLUE.

17. When should a collection pipeline use asSequence() instead of plain filter/map?

When intermediate stages would each allocate a whole list — long pipelines, large inputs, or early termination via take/first. Sequences process one element through the entire chain lazily, so a take(3) after a million-element filter may only touch a few thousand elements. For three stages over fifty items, plain collections are simpler and fast enough.

Part 4 — Concurrency & systems

18. What's the practical difference between launch and async?

launch returns a Job — fire-and-forget, for side effects where you only need to wait or cancel. async returns a Deferred — it represents a value you'll await(). Using launch when you need a result forces an awkward shared variable; using async for pure effects invites you to await work that produces nothing.

19. Why does a while (true) { … } loop inside a coroutine ignore cancellation?

Cancellation is cooperative — it's only checked at suspension points (delay, withContext, suspending collections) or explicit checks. A tight loop never hits one, so cancel() sets the flag and nothing happens. Call ensureActive() or yield() each iteration. And never swallow CancellationException in a catch — rethrow it.

20. A Kotlin function returns User? and Java calls it. What goes wrong?

Java sees a platform type (User!) — nullability isn't visible, so it dereferences without warning and you get a runtime NPE instead of a compile error. Annotate the Kotlin declaration with @Nullable (JetBrains or JSR-305) so Java's compiler and IDE can flag it. This is the boundary where Kotlin's guarantees stop.
